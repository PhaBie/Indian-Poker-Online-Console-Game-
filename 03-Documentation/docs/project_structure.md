# โครงสร้างและวงจรการทำงานของระบบ (Project Structure & System Lifecycle)

เอกสารฉบับนี้อธิบายภาพรวมสถาปัตยกรรม วงจรการทำงานตั้งแต่เริ่มต้นจนสิ้นสุดรอบเกม (Lifecycle) และการแบ่งหน้าที่ความรับผิดชอบของโมดูลต่างๆ ในโครงการ **Indian Poker Online (Teen Patti)**

---

## 1. ภาพรวมสถาปัตยกรรม (Architectural Overview)

- **รูปแบบสถาปัตยกรรม:** Client-Server แบบรวมศูนย์ (Authoritative Server) โดยสื่อสารแบบ Real-time ผ่านโพรโทคอล WebSocket
- **เทคโนโลยีหลัก:** ภาษา TypeScript รันบน Bun Runtime โดยฝั่ง Client ใช้ React ร่วมกับไลบรารี Ink สำหรับเรนเดอร์หน้าจอบน Terminal
- **หลักการแบ่งแยกหน้าที่ (Separation of Concerns):**
  - **Client:** ทำหน้าที่แสดงผลส่วนติดต่อผู้ใช้ (Terminal UI) รับอินพุตจากแป้นพิมพ์ และส่งคำสั่งการกระทำไปยังเซิร์ฟเวอร์เท่านั้น โดยไม่มีสิทธิ์ตัดสินผลหรือเปลี่ยนแปลงข้อมูลเกม
  - **Server:** เป็นศูนย์กลางการตัดสินใจ (Single Source of Truth) ตรวจสอบความถูกต้องของคำสั่ง ควบคุมกติกาเกม และจัดสรรชิปเงินรางวัล
  - **Core Logic:** แยกตรรกะกติกาของเกมเป็นฟังก์ชันบริสุทธิ์ (Pure Functions) ไม่ขึ้นต่อระบบเครือข่ายหรือระบบไฟล์ เพื่อให้ง่ายต่อการทดสอบระดับหน่วย (Unit Test)

---

## 2. วงจรการทำงานของระบบ (System Lifecycle & Sequence)

กระบวนการทำงานของระบบจำแนกออกเป็น 4 ขั้นตอนหลัก ดังนี้:

### ขั้นตอนที่ 1: การเริ่มทำงานของเซิร์ฟเวอร์ (Server Initialization)

1. เริ่มต้นระบบผ่าน `01-Source-code/server/index.ts` (สำหรับ Local Network / LAN) หรือ `01-Source-code/server/online.ts` (สำหรับการเชื่อมต่อข้ามเครือข่ายผ่าน Tunnel)
2. เซิร์ฟเวอร์เปิดรับการเชื่อมต่อผ่าน WebSocket Server และเตรียมพร้อมอินสแตนซ์ของ `RoomManager` เพื่อรองรับการจัดการห้องแข่งขัน

### ขั้นตอนที่ 2: การเชื่อมต่อของผู้เล่นและการยืนยันตัวตน (Client Handshake & Connection)

1. ผู้เล่นเปิดแอปพลิเคชันไคลเอนต์ ระบุที่อยู่ IP ของเซิร์ฟเวอร์ และชื่อผู้เล่น (`PlayerName`)
2. ไคลเอนต์ส่งคำขอเชื่อมต่อไปยังเซิร์ฟเวอร์
3. โมดูล `socketHandler.ts` รับการเชื่อมต่อ และส่งข้อมูลให้ `validator.ts` ตรวจสอบความถูกต้องของรูปแบบข้อมูล (เช่น ความยาวของชื่อ และตัวอักขระที่อนุญาต)
4. เมื่อผ่านการตรวจสอบ เซิร์ฟเวอร์จะตอบรับการเชื่อมต่อและสร้าง Session Token ให้แก่ผู้เล่น เพื่อใช้สำหรับการกู้คืนสถานะกรณีการเชื่อมต่อขัดข้อง (Reconnection)

### ขั้นตอนที่ 3: การจัดการห้องแข่งขัน (Room Management & Lobby)

1. ผู้เล่นสามารถเลือก **สร้างห้องใหม่ (Create Room)** โดยกำหนดค่าธรรมเนียม Boot Amount หรือ **เข้าร่วมห้องที่มีอยู่ (Join Room)** ผ่าน Room ID
2. `RoomManager` ทำหน้าที่จัดสรรห้อง (`Room`) และบรรจุออบเจกต์ผู้เล่น (`Player`) เข้าสู่ห้องแข่งขัน
3. ห้องแข่งขันรองรับผู้เล่นจำนวน 2 ถึง 4 คน โดยต้องมีผู้เล่นอย่างน้อย 2 คนขึ้นไปจึงจะสามารถเริ่มเกมได้
4. กรณีมีผู้เล่นใหม่เข้าร่วมระหว่างที่เกมกำลังดำเนินอยู่ ผู้เล่นดังกล่าวจะถูกจัดให้อยู่ในสถานะสังเกตการณ์ (`WAITING`) จนกว่ารอบปัจจุบันจะสิ้นสุดลง
5. เมื่อผู้เล่นทุกคนอยู่ในสถานะพร้อม (`Ready`) หัวหน้าห้อง (Host) สามารถส่งคำสั่งเริ่มเกมได้

### ขั้นตอนที่ 4: วงรอบการดำเนินเกม (Game Loop & Round Progression)

วงรอบการแข่งขันใน 1 รอบ ประกอบด้วยลำดับขั้นดังนี้:
`เริ่มรอบใหม่` → `หักค่าธรรมเนียม Boot เข้า Pot` → `แจกไพ่คว่ำหน้าคนละ 3 ใบ` → `สลับเทิร์นวางเดิมพัน` → `ตัดสินผล Showdown` → `จัดสรรเงินรางวัล Pot` → `เริ่มรอบถัดไป`

1. **การเริ่มต้นรอบและการแจกไพ่ (Round Start & Dealing):**
   - ฟังก์ชัน `gameLogic.ts` ทำการสร้างสำรับไพ่ 52 ใบ สับไพ่ (รองรับการกำหนด Seed สำหรับการทดสอบ) และแจกไพ่ให้ผู้เล่นคนละ 3 ใบ
   - ผู้เล่นทุกคนเริ่มต้นรอบในสถานะ **Blind** (ยังไม่เปิดดูไพ่ในมือ)
2. **การดำเนินการในแต่ละเทิร์น (Turn Actions):**
   - ผู้เล่นในเทิร์นสามารถเลือกการกระทำได้ดังนี้:
     - **SEEN:** เปิดดูไพ่ของตนเอง ส่งผลให้อัตราเดิมพันขั้นต่ำในรอบถัดไปปรับเป็น 2 เท่า
     - **CALL:** วางเงินเดิมพันเทียบเท่าอัตราปัจจุบัน
     - **BET / RAISE:** ปรับเพิ่มอัตราเงินเดิมพัน ซึ่งส่งผลให้ผู้เล่นคนอื่นต้องวางเงินเพิ่มตาม
     - **FOLD:** หมอบและสละสิทธิ์ในรอบการแข่งขันปัจจุบัน
     - **SHOW:** ขอเปิดไพ่เปรียบเทียบแต้ม (กระทำได้เมื่อเหลือผู้เล่นที่ยังไม่หมอบ 2 คนสุดท้าย)
3. **เส้นทางการประมวลผลคำสั่ง (Action Processing Pipeline):**
   - ไคลเอนต์ส่งคำสั่ง Action ผ่าน WebSocket
   - `validator.ts` ตรวจสอบความถูกต้องของชนิดข้อมูลและโครงสร้าง Schema
   - `accessPolicy.ts` ตรวจสอบความถูกต้องของสิทธิ์ เช่น เป็นเทิร์นของผู้เล่นจริงหรือไม่ และมีชิปเพียงพอหรือไม่
   - `gameLogic.ts` ประมวลผลผลลัพธ์ตามกติกาของเกม
   - `GameState.ts` ปรับปรุงสถานะตัวแปรภายใน (ชิป, ยอดเงิน Pot, ลำดับเทิร์นถัดไป)
   - เซิร์ฟเวอร์แปลงข้อมูลเป็น Data Transfer Object (DTO) ที่กรองข้อมูลส่วนบุคคลออกแล้วบรอดแคสต์ส่งให้ไคลเอนต์ทุกคน
4. **การควบคุมการเข้าถึงข้อมูลไพ่ (Information Masking / Anti-Cheat):**
   - เซิร์ฟเวอร์จะตัดข้อมูลไพ่ส่วนบุคคลของผู้เล่นคนอื่นออกจาก Payload ก่อนส่งกระจายผ่านเครือข่ายเสมอ ไคลเอนต์จะไม่ได้รับข้อมูลไพ่ของคู่แข่งจนกว่าจะถึงขั้นตอนการเปิดไพ่ตัดสินผล
5. **การสิ้นสุดรอบและการจัดสรรเงินรางวัล (Round Resolution):**
   - **กรณีผู้เล่นหมอบจนเหลือคนสุดท้าย:** ผู้เล่นที่เหลืออยู่จะชนะทันทีและได้รับเงินทั้งหมดใน Pot โดยไม่ต้องเปิดไพ่
   - **กรณีขอ SHOW:** `gameLogic.ts` ทำการประเมินชุดไพ่ของผู้เล่นทั้งสองฝ่ายตามลำดับแต้มของ Teen Patti ผู้ชนะจะได้รับเงิน Pot หากแต้มเสมอกันระบบจะดำเนินการแบ่ง Pot (Split Pot) ตามข้อกำหนด

## 3. หน้าที่ความรับผิดชอบของโมดูลในระบบ (Module Responsibilities)

### 3.1 ชั้นประมวลผลกติกาและบริการ (Core Logic & Domain Services)

- **`01-Source-code/server/core/gameLogic.ts`**
  - ศูนย์กลางตรรกะกติกาของเกม ประกอบด้วยฟังก์ชันบริสุทธิ์ เช่น `createDeck()`, `shuffleDeck()`, `dealCards()`, `evaluateHand()`, `compareHands()` และ `calculateSplitPot()`
- **`01-Source-code/server/domain/services/RoomManager.ts`**
  - ตัวจัดการสารบบห้องแข่งขันส่วนกลาง ควบคุมการสร้าง ค้นหา ลบ และจัดสรรทรัพยากรห้องแข่งขันในระบบ

### 3.2 ชั้นแบบจำลองข้อมูล (Domain Models)

- **`01-Source-code/server/domain/models/Room.ts`**
  - แบบจำลองห้องแข่งขัน บันทึกข้อมูลรหัสห้อง, หัวหน้าห้อง, แผนผังผู้เล่น (`Map<string, Player>`) และสถานะเกม (`GameState`)
- **`01-Source-code/server/domain/models/Player.ts`**
  - แบบจำลองผู้เล่น ห่อหุ้มข้อมูลส่วนบุคคล เช่น ชิปคงเหลือ, เงินเดิมพันสะสม, สถานะความพร้อม, สถานะ Blind/Seen และไพ่ในมือ
- **`01-Source-code/server/domain/models/GameState.ts`**
  - ควบคุมสถานะเกมปัจจุบัน ได้แก่ ระยะของเกม (Phase), ยอดเงินใน Pot, อัตราเดิมพันปัจจุบัน และดัชนีผู้เล่นในเทิร์น
- **`01-Source-code/shared/types.ts`**
  - นิยามโครงสร้างข้อมูลร่วมและ DTOs ที่ใช้งานร่วมกันระหว่าง Client และ Server เพื่อป้องกันความผิดพลาดของชนิดข้อมูล

### 3.3 ชั้นเครือข่ายและความปลอดภัย (Network & Security Layer)

- **`01-Source-code/server/network/socketHandler.ts`**
  - รับข้อความเหตุการณ์จาก WebSocket ถอดรหัสคำสั่ง และส่งต่อการทำงานไปยัง Domain Models พร้อมทั้งบรอดแคสต์สถานะใหม่
- **`01-Source-code/server/network/validator.ts`**
  - ตรวจสอบความถูกต้องของโครงสร้างข้อมูลขาเข้า (Schema Validation ด้วย Zod) เพื่อป้องกันข้อมูลที่ไม่พึงประสงค์
- **`01-Source-code/server/network/accessPolicy.ts`**
  - ตรวจสอบสิทธิ์การเข้าถึงและการดำเนินคำสั่ง (Authorization & Turn Validation) เพื่อป้องกันการส่งคำสั่งข้ามเทิร์นหรือการกระทำผิดกติกา

### 3.4 ชั้นส่วนติดต่อผู้ใช้ (Client Presentation Layer)

- **`01-Source-code/client/network/SocketClient.ts`**
  - ตัวจัดการการเชื่อมต่อ WebSocket ฝั่งไคลเอนต์ รองรับการส่งคำสั่งและการรับฟังเหตุการณ์จากเซิร์ฟเวอร์
- **`01-Source-code/client/state/ClientState.ts`**
  - ตัวจัดการและจัดเก็บสถานะภายในของไคลเอนต์เพื่อส่งต่อให้แก่คอมโพเนนต์แสดงผล
- **`01-Source-code/client/ui/screens/`**
  - คอมโพเนนต์หน้าจอแสดงผลบน Terminal (React + Ink) แยกเป็น `MainMenuScreen`, `CreateRoomScreen`, `WaitingRoomScreen`, `GameScreen` และ `ResultScreen`
- **`01-Source-code/client/ui/controllers/`**
  - ตัวประสานงานและดักจับเหตุการณ์จากแป้นพิมพ์ (Keyboard Input Controllers) เพื่อแปลงเป็น Action ส่งไปยังเซิร์ฟเวอร์
