# Architecture & Design

โปรเจกต์นี้ได้รับการออกแบบเพื่อรองรับการทำงานแบบ Multiplayer Real-time บน Console โดยใช้เทคโนโลยีรันไทม์ Bun ร่วมกับ TypeScript

## โครงสร้างการทำงานของระบบ (Client-Server)

ระบบแบ่งหน้าที่หลักออกเป็น 3 ส่วนอย่างชัดเจน:

### 1. Client (ส่วนแสดงผลและรับคำสั่ง)

- ทำหน้าที่แสดงหน้าจอเกมผ่าน Terminal (ใช้ React + Ink)
- รับคำสั่งและ Input จากผู้เล่น
- ส่ง Action ไปยัง Server ผ่าน WebSocket
- **จะไม่ตัดสินใจ Logic ใดๆ เลย** เป็นเพียงแค่ View

### 2. Server (ส่วนควบคุมเกมหลัก)

- เป็นตัวควบคุมเกมทั้งหมดและเป็น Single Source of Truth
- ตรวจสอบว่า Action ของ Client นั้นถูกต้องและสามารถทำได้หรือไม่
- จัดการการเชื่อมต่อ WebSocket และ Session ของผู้เล่น
- ป้องกันการโกงโดยจะไม่ส่งข้อมูลไพ่ที่คว่ำอยู่ให้ผู้เล่นคนอื่น

### 3. Game Logic / Game State (ส่วนกติกาและสถานะ)

- เก็บกติกาและสถานะของเกม เช่น:
  - จำนวน Chips ของผู้เล่น
  - ไพ่ที่แจกให้แต่ละคน
  - จำนวนเงินรวมใน Pot
  - ลำดับเทิร์นและผู้เล่นที่กำลังตัดสินใจ

## หลักการออกแบบสถาปัตยกรรม

1. **การแบ่งแยกส่วนหน้าที่ (Separation of Concerns):** แยกส่วนแสดงผล (UI) ออกจากตรรกะประมวลผลของเกม ช่วยให้สามารถปรับเปลี่ยน UI ได้โดยไม่กระทบต่อ Game Logic
2. **การสนับสนุนการทดสอบ (Testability / TDD):** ตรรกะกติกาของเกม (`01-Source-code/server/core`) แยกตัวเป็นอิสระ ไม่ขึ้นกับ I/O ทำให้สามารถเขียน Unit Test ควบคุมทั้ง Happy Path, Unhappy Path และ Boundary Cases ได้อย่างสะดวกรวดเร็ว
3. **สัญญาข้อมูลร่วม (Single Source of Truth):** ใช้ `01-Source-code/shared/` เป็นศูนย์กลางกำหนด Data Types, Interfaces และรูปแบบข้อความ WebSocket ทำให้ Client และ Server สื่อสารบนมาตรฐานเดียวกันอย่างถูกต้อง
4. **ความง่ายต่อการบำรุงรักษาและการขยายระบบ (Maintainability & Scalability):** โครงสร้างแบบ Clean / Domain-Driven Architecture ช่วยให้สามารถขยายฟีเจอร์ใหม่และตรวจสอบแก้ไขข้อผิดพลาดได้ตรงจุด

## ข้อจำกัดที่ทราบ (Known Limitations)

ข้อจำกัดทางเทคนิคของระบบในเวอร์ชันปัจจุบัน:

1. ขนาดหน้าจอ Terminal แนะนำให้ใช้อย่างน้อย 150x41 คอลัมน์ เพื่อให้สามารถแสดงผลกระดานเกมและแผงควบคุมได้อย่างสมบูรณ์
2. ระบบถูกออกแบบเพื่อรองรับผู้เล่นสูงสุด 4 คนต่อหนึ่งห้องแข่งขันในเครือข่ายท้องถิ่น (LAN) หรือการเชื่อมต่อผ่าน Tunnel แบบผู้เล่นกลุ่มเล็ก
3. การบันทึกสถานะเซสชันในบางกรณีที่ขาดการเชื่อมต่ออย่างกะทันหันก่อนการเริ่มต้นผู้เล่นเสร็จสมบูรณ์ อาจทำให้ข้อมูลชื่อผู้เล่นไม่ถูกบันทึกลงไฟล์เซสชัน ซึ่งอยู่ระหว่างการปรับปรุงกลไกตรวจสอบก่อนเขียนไฟล์
