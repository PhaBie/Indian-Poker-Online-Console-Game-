# Design Decisions (บันทึกการตัดสินใจเชิงสถาปัตยกรรมและการออกแบบ)

เอกสารฉบับนี้จัดทำขึ้นเพื่อบันทึกเหตุผลและข้อพิจารณาทางวิศวกรรมซอฟต์แวร์ในการตัดสินใจเลือกเทคโนโลยี รูปแบบสถาปัตยกรรม และกระบวนทัศน์ในการพัฒนาระบบ **Indian Poker Online (Teen Patti)**

---

## 1. การเลือกภาษาและรันไทม์ (TypeScript + Bun)

- **เหตุผลที่เลือก TypeScript:**
  - เพิ่มความปลอดภัยด้านชนิดข้อมูล (Type Safety) ช่วยตรวจจับข้อผิดพลาดระหว่างการพัฒนา (Compile-time Errors) ก่อนนำไปรันจริง
  - ช่วยสร้างสัญญาข้อมูลร่วม (Shared Contracts) ระหว่าง Client และ Server ป้องกันปัญหา Data Mismatch
- **เหตุผลที่เลือก Bun:**
  - เป็นรันไทม์ความเร็วสูงที่มีตัวดำเนินการทดสอบในตัว (`bun test`) ทำให้การรัน Unit Test 536 ชุดทดสอบใช้เวลาเพียง ~570ms
  - รองรับ TypeScript และ JSX ได้โดยตรงโดยไม่ต้องตั้งค่า Transpiler ภายนอกที่ซับซ้อน
  - มีระบบจัดการแพ็กเกจที่รวดเร็วและใช้ทรัพยากรหน่วยความจำต่ำ

---

## 2. การเลือกใช้ React ร่วมกับ Ink สำหรับ Terminal UI

- **ข้อพิจารณา:** การพัฒนาเกมคอนโซลแบบเดิมมักใช้ `console.log` หรือไลบรารีประเภท ANSI Escape Sequences โดยตรง ซึ่งทำให้โค้ดจัดการหน้าจอกระจัดกระจายและยากต่อการจัดการสถานะ
- **การตัดสินใจ:**
  - เลือกใช้ **React 19 ร่วมกับ Ink 7** เพื่อนำแนวคิด Component-based Architecture และ Declarative UI มาปรับใช้บน Terminal
  - การเรนเดอร์หน้าจอถูกผูกเข้ากับ State ของเกม ทำให้เมื่อข้อมูลจาก WebSocket มีการอัปเดต หน้าจอจะถูกคำนวณและเรนเดอร์ใหม่เฉพาะส่วนที่จำเป็นโดยอัตโนมัติ
  - แยกหน้าจอออกเป็นคอมโพเนนต์ย่อยตามหน้าที่อย่างชัดเจน เช่น `LobbyScreen`, `GameScreen`, `ResultScreen`

---

## 3. การประยุกต์ใช้กระบวนทัศน์ OOP ร่วมกับ FP (Multi-Paradigm Architecture)

ระบบเลือกใช้จุดเด่นของทั้งสองกระบวนทัศน์ตามลักษณะของภาระงาน:

### 3.1 Object-Oriented Programming (OOP) สำหรับ Domain Models

- **ส่วนที่นำไปใช้:** `01-Source-code/server/domain/` (เช่น `Player`, `Room`, `RoomManager`, `GameState`)
- **เหตุผล:**
  - เหมาะสำหรับการจัดการวงจรชีวิตและสถานะที่มีการเปลี่ยนแปลง (Stateful Lifecycle Management)
  - นำหลักการห่อหุ้มข้อมูล (Encapsulation) มาใช้เพื่อป้องกันไม่ให้ภายนอกแก้ไขสถานะของ Player หรือ Room โดยตรง ต้องผ่าน Method ที่กำหนดเท่านั้น
  - สร้าง Hierarchy ของข้อผิดพลาดผ่าน `GameError` ซึ่งสืบทอดจากคลาส `Error` มาตรฐาน

### 3.2 Functional Programming (FP) สำหรับ Core Game Logic

- **ส่วนที่นำไปใช้:** `01-Source-code/server/core/gameLogic.ts`
- **เหตุผล:**
  - กติกาการตัดสินไพ่ (Hand Evaluation) และการคำนวณเงินกองกลาง (Split Pot) เหมาะกับการเขียนในรูปแบบ **ฟังก์ชันบริสุทธิ์ (Pure Functions)**
  - คืนค่าผลลัพธ์ใหม่โดยไม่แก้ไขข้อมูลนำเข้า (No Mutation / Immutability) และปราศจากผลข้างเคียง (No Side Effects)
  - ใช้ **ฟังก์ชันลำดับสูง (Higher-Order Functions)** เช่น `.map()`, `.filter()`, `.some()`, `.sort()`, `.reduce()` ช่วยให้อ่านโค้ดเข้าใจง่ายและลดความผิดพลาดเชิงคำนวณ
  - ช่วยให้การทำ Test-Driven Development (TDD) สะดวกรวดเร็ว สามารถระบุอินพุตและตรวจสอบผลลัพธ์ได้อย่างแม่นยำ

---

## 4. สถาปัตยกรรมแบบ Authoritative Server และการแยก Logic ออกจาก I/O

- **Authoritative Server:**
  - ให้เซิร์ฟเวอร์เป็นผู้ตัดสินผลและควบคุมสถานะเกมเพียงฝ่ายเดียว ไคลเอนต์ทำหน้าที่ส่ง Action และเรนเดอร์ข้อมูลตามที่ได้รับเท่านั้น
  - ป้องกันการทุจริต (Anti-Cheat): เซิร์ฟเวอร์จะตัดข้อมูลไพ่ของคู่แข่งออกจาก Payload ก่อนบรอดแคสต์ ทำให้ผู้เล่นไม่สามารถดักจับข้อมูลไพ่ของผู้อื่นได้จนกว่าจะถึงรอบเปิดไพ่
- **Decoupled Logic & I/O:**
  - Core Game Logic ใน `01-Source-code/server/core/` ถูกแยกขาดจาก Network Socket, File System และ Terminal Rendering
  - ทำให้สามารถทดสอบกติกาเกมได้โดยไม่ต้องจำลองการเชื่อมต่อเครือข่าย

---

## 5. การตรวจสอบความถูกต้องของข้อมูล (Schema Validation ด้วย Zod)

- **เหตุผลที่เลือก Zod:**
  - ใช้ตรวจสอบข้อมูลนำเข้าจากภายนอก (Runtime Validation) ทั้งข้อความคำสั่งจาก WebSocket และค่าตัวเลขต่างๆ
  - ป้องกันข้อมูลผิดปกติ เช่น การส่งเงินเดิมพันติดลบ, ค่าที่เป็นทศนิยม, ค่าสตริงแปลกปลอม หรือค่าเกินขอบเขตจำนวนเต็มปลอดภัย (`Number.MAX_SAFE_INTEGER`)
  - แปลง Schema ออกมาเป็น TypeScript Types ได้โดยตรง (Type Inference)

---

## 6. การจัดการความคงอยู่ของข้อมูล (Session JSON Persistence)

- **เหตุผลที่เลือก JSON File:**
  - มีความเรียบง่าย ไม่จำเป็นต้องติดตั้ง Database Engine ภายนอก ทำให้สะดวกต่อการตรวจงานและการรันบนเครื่องประเมินผล
  - ใช้สำหรับบันทึก Session Token เพื่อรองรับการเชื่อมต่อกลับ (Reconnection) กรณีผู้เล่นสัญญาณเครือข่ายขัดข้อง
  - ใช้บันทึกประวัติการแข่งขัน (Game History) เมื่อสิ้นสุดรอบสำหรับตรวจสอบย้อนหลัง
