# ข้อกำหนดการทำงานร่วมกันผ่านระบบควบคุมเวอร์ชัน (Git Workflow)

โครงการนี้กำหนดนโยบาย **Branch Protection** บนกิ่งหลัก เพื่อความปลอดภัยและความถูกต้องในการตรวจสอบโค้ด (Code Review)

**ข้อควรระวังสำคัญ:** ห้ามทำการ Push หรือแก้ไขโค้ดที่กิ่ง `main` หรือ `demo` โดยตรงโดยเด็ดขาด การเปลี่ยนแปลงทั้งหมดต้องดำเนินการผ่าน Pull Request (PR)

---

## ขั้นตอนการทำงาน (Development Workflow)

1. **การดึงข้อมูลล่าสุดจากเซิร์ฟเวอร์:**

   ```bash
   git checkout demo
   git pull origin demo
   ```

2. **การสร้างกิ่งฟีเจอร์แยกตามประเภทของงาน:**

   ```bash
   git checkout -b feature/ชื่อฟีเจอร์
   ```

   _(หรือ `bugfix/ชื่อปัญหา` สำหรับการแก้ไขข้อผิดพลาด หรือ `docs/ชื่อเอกสาร` สำหรับงานเอกสาร)_

3. **การบันทึกการเปลี่ยนแปลง (Commit):**

   ```bash
   git add .
   git commit -m "feat: อธิบายฟังก์ชันใหม่ที่พัฒนา"
   ```

   _หมายเหตุ: ข้อความ Commit ต้องเป็นไปตามมาตรฐาน Conventional Commits (เช่น `feat:`, `fix:`, `refactor:`, `test:`, `docs:`) โดยระบบ Husky และ Lint-Staged จะตรวจสอบและจัดรูปแบบโค้ดอัตโนมัติก่อน Commit_

4. **การส่งโค้ดขึ้นระบบรีโมต (Push):**

   ```bash
   git push -u origin feature/ชื่อฟีเจอร์
   ```

5. **การสร้างคำขอรวมโค้ด (Pull Request - PR):**
   เปิด Pull Request บน GitHub เพื่อขอรวมโค้ดเข้าสู่กิ่ง `demo` พร้อมทั้งระบุคำอธิบายสรุปการเปลี่ยนแปลง เหตุผล และผลการทดสอบให้ชัดเจน

6. **การตรวจสอบและอนุมัติโค้ด (Code Review & Merge):**
   Pull Request ต้องผ่านการตรวจสอบคุณภาพและได้รับการอนุมัติ (Approve) จากสมาชิกในทีมอย่างน้อย 1 คนก่อนดำเนินการ Merge

---

## มาตรฐานคุณภาพก่อนการส่งมอบโค้ด (Quality Gates)

ก่อนเปิด Pull Request หรือบันทึก Commit ต้องตรวจสอบให้ผ่านเกณฑ์ต่อไปนี้:

- `bun x tsc --noEmit` : ตรวจสอบความถูกต้องของประเภทข้อมูล TypeScript (0 Errors)
- `bun test` : ชุดทดสอบอัตโนมัติผ่านทั้งหมด (536 passed)
- `bun run lint` : ตรวจสอบรูปแบบโค้ดตามมาตรฐาน ESLint (0 Errors)
- `bun run format` : จัดรูปแบบเอกสารและโค้ดตามข้อกำหนด Prettier
