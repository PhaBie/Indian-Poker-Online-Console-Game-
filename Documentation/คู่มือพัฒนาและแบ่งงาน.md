# คู่มือการพัฒนาและแบ่งงาน (Development & Work Breakdown Guide)

เอกสารฉบับนี้จัดทำขึ้นเพื่อกำหนดมาตรฐานการทำงาน การแบ่งหน้าที่ และเป้าหมายของแต่ละส่วนประกอบในระบบ
โปรดอ่านและทำความเข้าใจขอบเขตงานของท่านก่อนเริ่มพัฒนา

---

## 📌 1. สถานะและภาพรวมของโปรเจกต์ (Project Overview)

- **เทคโนโลยีหลัก:** TypeScript, Bun, React + Ink (สำหรับหน้าจอ Console)
- **สถาปัตยกรรม:** แยกส่วนตรรกะการคำนวณ (Core Logic) ออกจากการจัดการสถานะ (Domain/State) อย่างชัดเจน
- **กระบวนการทำงาน:** ใช้ชุดทดสอบ (Unit Tests) เป็นตัวกำหนดเป้าหมายการเขียนโค้ด (Test-Driven Development: Red → Green → Refactor)
- **ผู้รับผิดชอบการตรวจรับงาน (Reviewers):** ภูภา (Project Manager) และ ตังค์ (QA) ส่วนสมาชิกท่านอื่นรับผิดชอบในฐานะ Developer

---

## 🔄 2. แผนผังการไหลของข้อมูล (Data Flow Architecture)

แผนผังด้านล่างแสดงเส้นทางการเชื่อมต่อข้อมูลจากฝั่งผู้เล่นไปยังเซิร์ฟเวอร์และกลับมาแสดงผล
(หมายเหตุ: บางส่วนอาจยังไม่ได้พัฒนาเสร็จสิ้น แต่กำหนดไว้เป็นโครงสร้างมาตรฐาน)

[ฝั่งผู้เล่น / Client]
ผู้เล่น (Player)
└─> หน้าจอ Ink (UI)
└─> SocketClient
└─> (ส่งข้อมูลผ่าน WebSocket) ─┐
│
[ฝั่งเซิร์ฟเวอร์ / Server] │
Validator & SocketHandler <───────────────────┘
├─> ตรวจสอบความถูกต้องของข้อมูล (Validation)
└─> RoomManager
└─> Room (ห้องเล่นเกม)
└─> GameState (สถานะเกม)
├─> Player (ข้อมูลผู้เล่น)
└─> Core Logic (ระบบคำนวณไพ่)
│
StorageManager <──────────┘ (บันทึกข้อมูลและสถานะเกม)

เซิร์ฟเวอร์จะเป็น "ผู้ตัดสินขาด" (Source of Truth) ในเรื่องการเดิมพัน, ลำดับเทิร์น, การตัดสินผู้ชนะ และยอดเงินเสมอ ฝั่ง Client มีหน้าที่เพียงส่งคำสั่งและแสดงผลตามที่เซิร์ฟเวอร์ตอบกลับเท่านั้น

## 🛠️ 3. การแบ่งงานตามโมดูล (Module Breakdown)

### 3.1. Core: ระบบไพ่ การประเมินผล และการคำนวณเงิน

- **ไฟล์หลัก:** `src/server/core/gameLogic.ts`
- **ชุดทดสอบ:** `Test/core/gameLogic.*.test.ts` (รันด้วยคำสั่ง: `bun run test:logic`)

- **`createDeck`**: สร้างสำรับไพ่มาตรฐาน 52 ใบ (ห้ามมีใบซ้ำ)
- **`shuffleDeck`**: สลับไพ่โดยรับค่า RNG เข้ามาเพื่อใช้ควบคุมการสุ่มในโหมดทดสอบ (Test)
- **`dealCards`**: แจกไพ่แบบวนรอบทีละใบ ส่งคืนไพ่บนมือผู้เล่นและไพ่ที่เหลือในกอง
- **`evaluateHand`**: ประเมินความแข็งแกร่งของมือไพ่ตามกติกา Teen Patti ฉบับ Pagat
- **`compareHands`**: เปรียบเทียบมือไพ่เพื่อหาผู้ชนะ (รองรับกรณี A-2-3 ชนะ A-K-Q และไพ่เสมอ)
- **`getWinners`**: ประมวลผลกลุ่มผู้เล่นและส่งคืน ID ของผู้ชนะ (อาจมีมากกว่า 1 คนในกรณีเสมอ)
- **`calculateSplitPot`**: [ส่วนเสริม] ระบบแบ่งเงินกองกลาง (Pot) เป็นจำนวนเต็ม และปัดเศษให้ตามลำดับ

> **ข้อควรระวัง:** ห้ามดึงข้อมูลสถานะจาก Room มาใช้ใน Core เด็ดขาด ให้ใช้เฉพาะตัวแปรพื้นฐานเช่น `Card` และ `HandRank`

### 3.2. Player: สถานะส่วนตัวและการเดิมพัน

- **ไฟล์หลัก:** `src/server/domain/models/Player.ts`
- **ชุดทดสอบ:** `Test/domain/player.test.ts`

**เงื่อนไขการทำงาน:**

- **สถานะ Blind/Seen:** ผู้เล่นทุกคนต้องเริ่มด้วยสถานะ `Blind` เสมอ เมื่อเรียกฟังก์ชัน `seeCards()` จึงจะเปลี่ยนเป็น `Seen` และต้องกลับไปเป็น `Blind` เมื่อจบและเริ่มรอบใหม่ (`resetForNewRound()`)
- **การเดิมพัน (payBet):** ระบบต้อง "หักชิปตามยอดที่ส่งมาเต็มจำนวน" และ "นำไปบวกเพิ่มในยอดสะสม (bet)" ห้ามนำยอด bet ปัจจุบันไปหักลบเพื่อหาค่าส่วนต่างในการจ่าย
- ข้อมูล `privateCards` ต้องถูกปกปิดไว้ ไม่นำไปบันทึกลงใน Public DTO

### 3.3. GameState: การควบคุมสถานะในหนึ่งรอบเกม

- **ไฟล์หลัก:** `src/server/domain/models/GameState.ts`
- **ชุดทดสอบ:** `Test/domain/gameState.test.ts`

**เงื่อนไขการทำงาน:**

- **การขอดูไพ่ (Show):**
  - ทำได้ก็ต่อเมื่อเหลือผู้เล่น 2 คนในวงเท่านั้น
  - `Blind` ขอ Show เสีย 1 เท่าของ currentStake / `Seen` ขอ Show กับ `Seen` เสีย 2 เท่า
  - `Seen` ห้ามขอ Show กับ `Blind` โดยเด็ดขาด
  - หากแต้มเสมอ ผู้ที่เอ่ยปากขอ Show จะถูกปรับแพ้ทันที
- **ชนะบาย (Last Man Standing):** หากผู้เล่นคนอื่นหมอบ (Fold) หมดจนเหลือ 1 คน ให้ชนะรับเงินทันทีโดยไม่ต้องเปิดไพ่
- การเรียก `CALL` และ `RAISE` ต้องอัปเดตยอด `currentStake` ตามสัดส่วนกติกา และหักเงินผู้เล่นพร้อมนำเข้ากองกลาง (Pot) ให้ถูกต้อง

### 3.4. Room & RoomManager: การจัดการห้องเล่นเกม

- **ไฟล์หลัก:** `src/server/domain/models/Room.ts` และ `RoomManager.ts`
- **ชุดทดสอบ:** `Test/domain/room.test.ts` และ `roomManager.test.ts`

**เงื่อนไขการทำงาน:**

- ห้องหนึ่งรองรับผู้เล่นสูงสุด 4 คน เริ่มเกมได้เมื่อมี 2 คนขึ้นไป
- ผู้เล่นที่เข้ามากลางคันจะอยู่ในสถานะ `WAITING` จนกว่าจะเริ่มรอบถัดไป
- ฟังก์ชัน `reconnect` คาดหวังว่าจะได้รับ Player ID ที่ผ่านการตรวจสอบสิทธิ์ (Auth) มาแล้ว

### 3.5. Storage: ระบบบันทึกและกู้คืนข้อมูล

- **ไฟล์หลัก:** `src/server/infrastructure/StorageManager.ts`
- **ชุดทดสอบ:** `Test/infrastructure/storageManager.test.ts`

**เงื่อนไขการทำงาน:**

- ต้องจัดการบันทึกข้อมูลห้อง (Save) และกู้คืน (Load) ให้สามารถทำงานต่อได้จริง
- ข้อมูลที่บันทึกลงไฟล์เซิร์ฟเวอร์ต้องเก็บไพ่บนมือผู้เล่นอย่างครบถ้วน (แยกต่างหากจาก Public DTO ที่ใช้ส่งให้ Client)

### 3.6. Network & Server: การเชื่อมต่อและ WebSocket

- **ไฟล์หลัก:** `src/server/network/socketHandler.ts` และ `src/server/index.ts`
- **ชุดทดสอบ:** `Test/network/socketHandler.test.ts`

**เงื่อนไขการทำงาน:**

- ระบบจะอ้างอิงตัวตนจาก Session ที่ได้รับการตรวจสอบแล้วเท่านั้น (ไม่เชื่อ Player ID ที่แนบมากับ Payload ดิบ)
- การส่งข้อมูล `GAME_STATE_UPDATE` ต้องกรอง `privateCards` ทิ้งเสมอ ยกเว้นผลลัพธ์การ Show ในตอนจบเกม
- ผู้เล่นสถานะ `Blind` บนเซิร์ฟเวอร์จะต้องมีไพ่จริงๆ ครบถ้วน (เพื่อประโยชน์ในการ Save เกม) แต่ Network ต้องส่ง array ว่าง `[]` ไปให้หน้าจอ Client จนกว่าผู้เล่นจะกด `SEEN`

### 3.7. Client (React + Ink): ส่วนแสดงผลหน้าจอ

- **ตำแหน่งไฟล์:** `src/client/...`

**เงื่อนไขการทำงาน:**

- พัฒนาโครงสร้างการเชื่อมต่อ WebSocket ให้เสถียร (Connect/Disconnect/Reconnect)
- เตรียม UI Hooks และ ClientState ไว้รองรับการวาดหน้าจอ (Screens) ด้วย React + Ink
- เริ่มพัฒนาหน้าจอจำลอง (Mock UI) ก่อนเชื่อมกับ Server จริงเพื่อตกลงรูปแบบ Event

## ⚙️ 4. ข้อกำหนดส่วนกลาง (Shared Resources)

- **`src/shared/types.ts`**
  กำหนดโครงสร้างข้อมูล (Interfaces / DTOs) ที่ใช้ร่วมกันระหว่าง Client และ Server
- **`src/shared/constants.ts`**
  รวบรวมค่าคงที่ของระบบ เช่น เวลา Timeout หรือค่า Boot ตั้งต้น
- **`src/server/domain/errors/...`**
  รวบรวมประเภทข้อผิดพลาด (GameError) ที่เป็นมาตรฐานเดียวกัน
- **`eslint.config.mjs`**
  มาตรฐานการตรวจสอบความสะอาดของโค้ด (Linting)
- **`package.json`**
  แหล่งรวมสคริปต์คำสั่งและรายการไลบรารีที่จำเป็น

> **ข้อควรระวัง:** การแก้ไขไฟล์ในหมวดนี้ ต้องได้รับการยินยอมจากผู้ที่เกี่ยวข้องทั้งฝั่งต้นทางและปลายทาง ห้ามแอบแก้ไขเพียงเพื่อให้ Test ของตนเองผ่านโดยพลการ

## 🚀 5. ขั้นตอนและมาตรฐานก่อนส่งมอบงาน (Pre-Commit Checklist)

1. **ลำดับการเชื่อมต่อระบบ:**
   แนะนำให้พัฒนาจากแกนกลางออกมาข้างนอก: `Core -> Player -> GameState/Room -> Storage -> Network -> Client`

2. **ก่อนเปิด Pull Request (PR) ทุกครั้ง ต้องรันคำสั่งต่อไปนี้ให้ผ่านทั้งหมด:**

   ```bash
   bun run lint
   bunx tsc --noEmit
   bun run test:logic
   ```

   _(หมายเหตุ: หากท่านพัฒนาในส่วนอื่นๆ กรุณาแก้ไขเส้นทางของคำสั่งรัน Test ให้ตรงกับโฟลเดอร์ของท่าน)_

3. **มาตรฐานการทดสอบ:**
   - ห้ามแก้ไข Expected Result เพียงเพื่อให้เทสต์ผ่านสีเขียว หากลอจิกขัดแย้งกับกติกาให้แก้ที่ลอจิก
   - ไม่เขียนคำอธิบายด้วยคอมเมนต์ในไฟล์ Test ให้ใช้ชื่อ Test เป็นภาษาไทยที่บอกพฤติกรรมชัดเจน
   - ลบขีดล่าง `_` หน้าตัวแปรออกเมื่อท่านเริ่มเรียกใช้งานตัวแปรนั้นแล้ว
   - การพึ่งพา `Husky` (Pre-commit hook) เป็นเพียงการป้องกันเบื้องต้นบนเครื่องท่าน ห้ามละเลยการรีวิวโค้ดร่วมกัน
