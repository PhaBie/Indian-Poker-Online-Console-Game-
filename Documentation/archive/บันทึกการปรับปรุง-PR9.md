# บันทึกการปรับปรุงโครงการใน PR #9

PR นี้เตรียมโครงสร้างและข้อกำหนดทดสอบสำหรับการพัฒนา Indian Poker Online Console Game โดยปรับชุดทดสอบให้ตรวจพฤติกรรมได้ชัดเจนขึ้น จัดรูปแบบข้อมูลที่แต่ละส่วนใช้ร่วมกัน และเพิ่มเครื่องมือตรวจมาตรฐานโค้ดสำหรับทีม

งานในรอบนี้มุ่งเตรียมพื้นฐานก่อนพัฒนาฟีเจอร์ ฟังก์ชันหลักส่วนใหญ่ยังเป็น Stub จึงยังไม่ใช่ระบบที่เล่นได้ครบวงจร

## 1. ปรับชุดทดสอบให้สอดคล้องกับพฤติกรรมที่ต้องการ

| ส่วนงาน     | สิ่งที่ปรับปรุง                                                                            | ผลต่อการพัฒนา                                                     |
| ----------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| Player      | เตรียมไพ่ สถานะ และยอดเดิมพันก่อนทดสอบ reset พร้อมตรวจว่าชิปคงเหลือเท่าเดิม                | แยกการล้างข้อมูลรอบเก่าออกจากการคืนเงิน                           |
| Room        | ตรวจข้อมูลผู้เล่นใน Public State และการเปลี่ยนจาก ENDED กลับเป็น LOBBY                     | กำหนดผลลัพธ์ของการ reset และข้อมูลที่เปิดเผยได้                   |
| RoomManager | สร้างหลายห้องก่อนทดสอบลบห้องเป้าหมาย                                                       | ป้องกันการลบห้องอื่นโดยไม่ตั้งใจ                                  |
| GameState   | ใช้ fixture ตามบริบทและทดสอบ Boot ที่ต่างจากค่าเริ่มต้น                                    | ให้การเตรียมสถานะตรงกับ action และลดการกำหนดค่าตายตัว             |
| Core        | ควบคุม RNG ตรวจลำดับไพ่และการไม่แก้ input รวมถึงยอดแบ่งกองกลางและเศษชิป                    | ทำให้ผลทดสอบแน่นอนและตรวจผลคำนวณได้ตรงจุด                         |
| Network     | ตรวจการส่งข้อมูลหลาย socket ไพ่ตามผู้รับ และการปฏิเสธ token ไม่ถูกต้อง                     | กำหนดขอบเขตการส่งข้อมูลและการยืนยันตัวตน                          |
| Storage     | ตรวจไฟล์จริง โหลดผ่าน instance ใหม่ และตรวจไพ่ที่กู้คืน พร้อมล้างโฟลเดอร์ชั่วคราวหลังทดสอบ | ตรวจการบันทึกข้อมูลจริง ไม่พึ่งข้อมูลในหน่วยความจำเพียงอย่างเดียว |
| Client      | ใช้ fake transport จำลองเหตุการณ์เชื่อมต่อสำเร็จ                                           | ทดสอบสถานะการเชื่อมต่อโดยไม่ต้องเปิดเครือข่ายจริง                 |

ปรับชื่อกรณีทดสอบเป็นภาษาไทยและนำคอมเมนต์ใน Test ออกตามข้อตกลงของทีม โดยใช้ชื่อกรณีทดสอบและตัวแปรอธิบายเจตนาแทน

- ตังค์ : ใน test ชื่อคำอธิบายมันสื่ออยู่แล้วว่า Test อะไร เลยคิดว่าไม่ต้องเขียนคอมเม้นในไฟล์ test เลย คลีนๆดี

## 2. ปรับรูปแบบข้อมูลและความรับผิดชอบของแต่ละส่วน

- กำหนดความจุห้องสูงสุด 4 คน และค่า Boot เริ่มต้น 50 โดยต้องรองรับค่าที่ตั้งให้แต่ละห้อง
- ใช้ `raiseTo` เพื่อสื่อว่าจำนวนที่รับคือยอดเดิมพันเป้าหมาย และหักชิปเฉพาะส่วนต่าง
- ให้ `shuffleDeck` รับ RNG สำหรับควบคุมผลการสุ่มใน Test
- แยกการคำนวณแบ่งกองกลางเป็น `calculateSplitPot` และรองรับผู้ชนะหลายคน
- เพิ่ม `NetworkContext` เพื่อส่ง RoomManager, sessionStore และข้อมูล socket/session ให้ handler
- ใช้ `SESSION_CREATED` และ `JOIN_ROOM` พร้อม reconnectToken สำหรับการกลับเข้าห้อง
- ให้ Network ตรวจ token ก่อนเรียก `Room.reconnect(playerId)`
- แยก Public DTO ที่ไม่เปิดเผยไพ่ส่วนตัวออกจากข้อมูลบันทึกเกมที่ต้องใช้กู้คืน
- ใช้ประเภทข้อผิดพลาดเฉพาะกรณีเพื่อให้ Test และ Network ระบุสาเหตุได้ชัดเจน

รูปแบบเหล่านี้เป็นข้อตกลงตั้งต้น การเชื่อม dependencies และลอจิกจริงยังเป็นงานของแต่ละส่วนตามคู่มือพัฒนา

## 3. เตรียม React + Ink สำหรับทีม UI

เพิ่ม dependencies ของ React, Ink และชนิดข้อมูลที่เกี่ยวข้อง พร้อมตั้งค่า TypeScript ให้รองรับ JSX และเตรียมโฟลเดอร์ใน `src/client/ui/` ดังนี้:

| โฟลเดอร์      | หน้าที่                                            |
| ------------- | -------------------------------------------------- |
| `components/` | ส่วนแสดงผลที่ใช้ซ้ำ                                |
| `screens/`    | หน้าจอห้องรอ โต๊ะเกม และผลการแข่งขัน               |
| `hooks/`      | เชื่อม state, subscription และ input เข้ากับ React |
| `theme/`      | สีและค่ารูปแบบที่ใช้ร่วมกัน                        |

`LobbyUI.ts` และ `GameUI.ts` ยังเป็น class contracts เดิม ไม่ใช่ React components ทีม UI ต้องกำหนดบทบาทของไฟล์เหล่านี้ร่วมกับหน้าจอใหม่ รวมถึงพัฒนา App และ entry point ต่อ

## 4. เพิ่มเครื่องมือตรวจมาตรฐานโค้ด

- แยกกฎ ESLint สำหรับ Source, UI และ Test พร้อมเปิดการตรวจที่อาศัยข้อมูลชนิดจาก TypeScript
- อนุญาต PascalCase สำหรับฟังก์ชันและตัวแปรใน UI โดยยังคงกฎพื้นฐานของส่วนอื่น
- ยกเว้นกฎความยาวฟังก์ชัน ข้อความซ้ำ และฟังก์ชันเหมือนกันใน Test
- ใช้ type imports ลด explicit any และกำหนด `PlayerFixture` ให้ตรวจข้อมูลตั้งแต่ประกาศ
- เติม underscore ให้พารามิเตอร์ Stub ที่ยังไม่ใช้งาน โดยรักษาพฤติกรรมเดิมของ Source
- ปรับเวอร์ชัน ESLint ให้เข้ากับปลั๊กอิน และระบุ TypeScript เป็น dev dependency
- เพิ่ม Husky และ lint-staged ให้ตรวจไฟล์ TypeScript ที่ stage ใน `src/` และ `Test/` ก่อน commit
- เก็บ dependencies ผ่าน `bun.lock` และลบไฟล์ทดลอง `testSum.ts`

Hook เป็นเครื่องมือช่วยตรวจบนเครื่องผู้พัฒนา การรีวิวโค้ดและการตรวจใน CI ยังต้องจัดการแยกต่างหาก

## 5. ผลตรวจและสถานะก่อนเริ่มพัฒนา

| การตรวจ             | ผลในรอบเตรียมโครงสร้าง                                 |
| ------------------- | ------------------------------------------------------ |
| ESLint              | ผ่าน โดยไม่มี error หรือ warning                       |
| TypeScript compiler | ผ่าน                                                   |
| Husky / lint-staged | ทำงานและตรวจไฟล์ TypeScript ระหว่าง commit สำเร็จ      |
| ชุดทดสอบ            | ผลที่บันทึกไว้จากรอบพัฒนา: 82 เคส ผ่าน 3 และล้มเหลว 79 |

ฟังก์ชันส่วนใหญ่ยังเป็น Stub ทีมต้องตรวจสาเหตุของ Test ที่ล้มเหลวเมื่อเริ่มแต่ละฟีเจอร์ และพัฒนาตามรอบ Red → Green → Refactor จำนวน Test ที่ผ่านหรือล้มเหลวเพียงอย่างเดียวไม่ยืนยันความครบถ้วนของระบบ

## 6. งานที่ต้องทำต่อ

- เติม Core, Player, GameState และ Room ตามชุดทดสอบ
- พัฒนา schema และการตรวจข้อมูล JSON สำหรับบันทึกและกู้คืนเกม
- เชื่อม sessionStore, Storage และ WebSocket เข้ากับ Server จริง
- พัฒนา ClientState, subscriptions และหน้าจอ React + Ink
- เพิ่มการทดสอบการเชื่อมระบบเมื่อแต่ละส่วนพร้อม ปัจจุบัน reconnect Test ยังใช้ handler กับ mock session store
- เพิ่ม CI สำหรับตรวจงานก่อน merge
