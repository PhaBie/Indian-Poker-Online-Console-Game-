# Indian Poker Online (Console Game) 🃏

## Game Overview

เกมไพ่ Indian Poker Online แบบ Multiplayer ที่เล่นผ่านหน้าจอ Console หรือ Terminal โดยไม่ใช้เว็บบราวเซอร์ ใช้วิธีการเชื่อมต่อแบบ Client-Server ผ่าน WebSocket เพื่อสื่อสารกันแบบ Real-time ทำให้สามารถรองรับผู้เล่นหลายคนพร้อมกันได้

เทคโนโลยีและโครงสร้างหลักของระบบเขียนด้วย TypeScript และรันบน Bun โดยใช้ React+Ink ในการวาดหน้าจอ Terminal ฝั่งผู้เล่น ส่วนฝั่ง Server ออกแบบให้แยกส่วนของกติกาเกม (Game Logic) ออกมาอย่างชัดเจน เพื่อให้สามารถทำ Unit Test (TDD) และตรวจสอบความถูกต้องของระบบได้อย่างแม่นยำ

## รูปแบบการเล่นในแต่ละรอบเกม

1. สร้างห้อง / เข้าห้อง
2. ทุกคนลงขัน Boot เข้าสู่ Pot
3. แจกไพ่คว่ำหน้าคนละ 3 ใบ
4. วนเทิร์นเดิมพัน โดยเลือกว่าจะเป็น Blind หรือ Seen
5. สามารถ บัฟ / ตาม / เกทับ / หมอบ
6. เมื่อเหลือผู้เล่น 2 คน สามารถ SHOW หรือหากผู้เล่นคนอื่นหมอบจนเหลือผู้เล่นคนสุดท้าย ผู้เล่นคนนั้นจะชนะ
7. ผู้ชนะรับเงินทั้งหมดใน Pot แล้วเริ่มรอบใหม่

## กลไกการเล่น (Game Mechanics)

ระบบเปิดโอกาสให้ผู้เล่นเลือกแนวทางการเล่นระหว่างสถานะ Blind และ Seen ซึ่งส่งผลต่ออัตราการวางเงินเดิมพันและความเสี่ยง:

- **Blind** — ผู้เล่นไม่เปิดดูหน้าไพ่ของตนเอง มีข้อกำหนดให้วางเงินเดิมพันขั้นต่ำในอัตรา 1 เท่า ช่วยประหยัดเงินกองทุนและสร้างแรงกดดันต่อคู่แข่ง
- **Seen** — ผู้เล่นเปิดดูหน้าไพ่ของตนเองแล้ว ต้องวางเงินเดิมพันในอัตรา 2 เท่าเพื่อแลกกับการทราบข้อมูลไพ่ในมือ

## ส่วนติดต่อผู้ใช้งานบนเทอร์มินัล (Terminal UI)

ประยุกต์ใช้ React ร่วมกับไลบรารี Ink สำหรับเรนเดอร์คอมโพเนนต์บนเทอร์มินัลแทนการพิมพ์ข้อความบรรทัดคำสั่งทั่วไป ช่วยจัดระเบียบหน้าจอแสดงผล เมนูตัวเลือก และการตอบสนองต่อคีย์บอร์ดได้อย่างเป็นระเบียบและแม่นยำ

## ความปลอดภัยและการควบคุมข้อมูลไพ่ (Data Privacy & Integrity)

สถาปัตยกรรมแบบ Authoritative Server กำหนดให้เซิร์ฟเวอร์เป็นศูนย์กลางการประมวลผลเพียงฝ่ายเดียว โดยเซิร์ฟเวอร์จะตัดข้อมูลไพ่ของผู้เล่นคนอื่นออกจากชุดข้อมูลก่อนส่งกระจายผ่านเครือข่าย ส่งผลให้ไคลเอนต์ไม่สามารถล่วงรู้ข้อมูลไพ่ของคู่แข่งได้จนกว่าจะถึงขั้นตอนเปิดไพ่ตัดสินผล (Showdown)

## การจัดการเซสชันและการกู้คืนการเชื่อมต่อ (Reconnection)

ระบบสร้าง Session Token ประจำตัวผู้เล่นและบันทึกลงไฟล์ JSON เพื่อให้ผู้เล่นที่สัญญาณเครือข่ายขัดข้องสามารถกลับเข้าสู่ตำแหน่งเดิมในห้องแข่งขันได้โดยที่สถานะเกมและจำนวนชิปยังคงเดิม

## โครงสร้างการทำงานของระบบ

ระบบแบ่งหน้าที่หลักออกเป็น 3 ส่วน

**Client**
ทำหน้าที่:

- แสดงหน้าจอเกม
- รับคำสั่งจากผู้เล่น
- ส่ง Action ไปยัง Server

**Server**
เป็นส่วนที่ควบคุมเกมทั้งหมด เช่น:

- ตรวจสอบว่า Action สามารถทำได้หรือไม่
- คำนวณการเดิมพัน
- จัดการไพ่
- ตัดสินผู้ชนะ

**Game Logic / Game State**
เก็บกติกาและสถานะของเกม เช่น:

- จำนวน Chips ของผู้เล่น
- ไพ่
- จำนวนเงินใน Pot
- ผู้เล่นที่กำลังเล่น
- ลำดับเทิร์น

## เป้าหมายของเกม

เป้าหมายหลักของผู้เล่นคือ ชนะและรับเงินทั้งหมดใน Pot
สามารถชนะได้จาก 2 วิธี:

1. ทำให้ผู้เล่นคนอื่น FOLD จนเหลือตัวเองเป็นผู้เล่นคนสุดท้าย
2. เล่นจนเหลือผู้เล่น 2 คน แล้ว SHOW เพื่อเปิดไพ่เปรียบเทียบกัน และเป็นฝ่ายที่มีไพ่ใหญ่กว่า

## Requirements

### 1. ระบบการเล่นเกม

**ระบบห้องและผู้เล่น**

- ผู้เล่นสามารถสร้างห้องและตั้งค่า Boot Amount ได้เอง
- ในหนึ่งห้องสามารถมีผู้เล่นได้ 2 – 4 คน
- ต้องมีผู้เล่นอย่างน้อย 2 คน จึงจะสามารถเริ่มเกมได้
- ถ้ามีผู้เล่นเข้ามาระหว่างที่เกมกำลังเล่นอยู่ ผู้เล่นคนนั้นจะต้องรอจนกว่ารอบปัจจุบันจะจบก่อน จึงจะสามารถเล่นได้

**ระบบไพ่และการเดิมพัน**

- ใช้ไพ่มาตรฐานทั้งหมด 52 ใบ และแจกให้ผู้เล่นคนละ 3 ใบ
- ระบบสับไพ่ต้องสามารถกำหนด Seed/RNG ได้ เพื่อให้สามารถควบคุมผลลัพธ์และใช้ในการทดสอบระบบได้
- ตอนเริ่มรอบ ผู้เล่นทุกคนจะเป็น Blind และจ่ายเดิมพันในราคาปกติ
- เมื่อผู้เล่นเลือก SEEN เพื่อเปิดดูไพ่ของตัวเอง จะเปลี่ยนเป็น Seen และต้องจ่ายเดิมพันเป็น 2 เท่าตลอดรอบนั้น
- ผู้เล่นสามารถเลือกคำสั่งต่าง ๆ ได้ เช่น CALL, BET, RAISE, FOLD, SEEN และ SHOW

**การขอ SHOW**

- สามารถขอ SHOW ได้เมื่อเหลือผู้เล่นที่ยังเล่นอยู่เพียง 2 คน
- ผู้เล่นที่เป็น Seen ไม่สามารถขอ SHOW ใส่ผู้เล่นที่ยังเป็น Blind ได้
- หากคะแนนไพ่เสมอกัน คนที่เป็นฝ่ายขอ SHOW จะถือว่าแพ้

**การเรียงลำดับไพ่**
ลำดับไพ่จากใหญ่ไปเล็กคือ
ตอง > เรียงสี > เรียงธรรมดา > สี > คู่ > ไพ่สูง
โดยมีเงื่อนไขพิเศษคือ A-2-3 ถือเป็นไพ่เรียงที่ใหญ่ที่สุด และใหญ่กว่า A-K-Q

**การแบ่งเงินใน Pot**

- ถ้าผู้เล่นคนอื่นหมอบหมด ผู้เล่นที่เหลือจะได้รับเงินใน Pot ทั้งหมด
- ถ้ามีการเปิดไพ่ ผู้เล่นที่ชนะจะได้รับเงินใน Pot
- หากมีกรณีที่ต้องแบ่งเงิน ระบบต้องรองรับการ Split Pot และจัดการเศษเงินให้ถูกต้อง

### 2. ระบบความปลอดภัยและความถูกต้อง

Server จะเป็นตัวหลักในการตัดสินทุกอย่าง เช่น

- ใครเป็นผู้ชนะ
- ผู้เล่นมีชิปเท่าไหร่
- ใครสามารถลงเดิมพันได้
- เกมอยู่ในสถานะไหน

ส่วน Client มีหน้าที่ส่งคำสั่งไปให้ Server และนำผลที่ Server ส่งกลับมาแสดงบนหน้าจอเท่านั้น

**การซ่อนไพ่**
ไพ่ของผู้เล่นต้องไม่ถูกส่งไปให้ผู้เล่นคนอื่นเห็นโดยเด็ดขาด

- ถ้ายังเป็น Blind จะยังไม่ส่งข้อมูลไพ่ให้เห็น
- ผู้เล่นจะเห็นไพ่ของตัวเองได้เมื่อเลือก SEEN
- ไพ่ของผู้เล่นทุกคนจะถูกเปิดเผยพร้อมกันเมื่อเกมจบและเข้าสู่หน้า `GAME_RESULT`

**การตรวจสอบข้อมูล**
ระบบต้องตรวจสอบข้อมูลก่อนนำไปใช้งาน เช่น

- ห้ามลงเงินติดลบ
- ห้ามใช้ตัวเลขที่มีทศนิยมถ้าระบบกำหนดให้ใช้จำนวนเต็ม
- ห้ามลงเงินเกินจำนวนที่กำหนด
- ห้ามมีไพ่ใบเดียวกันซ้ำกัน
- ถ้าเกิดข้อผิดพลาด ระบบต้องไม่ทำให้จำนวนเงินหรือสถานะเกมเสียหาย

### 3. ระบบเชื่อมต่อและการบันทึกเกม

**WebSocket**
เกมจะใช้ WebSocket สำหรับติดต่อระหว่าง Client กับ Server เพื่อให้ข้อมูลในเกมอัปเดตแบบ Real-time เช่น การลงเดิมพัน การหมอบ หรือการเปลี่ยนสถานะของผู้เล่น

**Reconnect**
เมื่อผู้เล่นเข้าห้อง ระบบจะสร้าง `reconnectToken` ให้
ถ้าอินเทอร์เน็ตหลุด ผู้เล่นสามารถใช้ Token เดิมเพื่อกลับเข้าห้องและเล่นต่อจากสถานะเดิมได้

**Save / Load**
ระบบสามารถบันทึกสถานะเกมเป็นไฟล์ JSON และสามารถโหลดกลับมาเล่นต่อได้ โดยข้อมูลสำคัญ เช่น ไพ่ ชิป และสถานะของเกมต้องไม่หาย

**ระบบแชท**
ผู้เล่นสามารถส่งข้อความพูดคุยกันภายในห้องระหว่างเล่นเกมได้

### 4. หน้าจอของเกม

ตัวเกมทำงานบน Console / Terminal โดยใช้ React 19 + Ink 7 แบ่งหน้าจอหลักออกเป็น 3 ส่วน

**LobbyScreen**
ใช้สำหรับ

- สร้างห้อง
- เข้าห้องด้วย Room ID
- ดูรายชื่อผู้เล่น
- รอผู้เล่นคนอื่นเข้าห้อง
- เริ่มเกม

**GameScreen**
เป็นหน้าหลักระหว่างเล่นเกม ใช้แสดง

- เงินใน Pot
- รายชื่อผู้เล่น
- จำนวนชิปของแต่ละคน
- สถานะ Blind / Seen
- ไพ่ของผู้เล่น
- คำสั่งที่สามารถเลือกได้ เช่น CALL, BET, RAISE, FOLD, SEEN และ SHOW

**ResultScreen**
แสดงผลหลังจบเกม เช่น

- ใครเป็นผู้ชนะ
- ผู้ชนะได้รับชิปเท่าไหร่
- ไพ่ของผู้เล่นแต่ละคน
- ผลการเปิดไพ่
- สรุปผลของรอบนั้น

### 5. มาตรฐานในการพัฒนา

**การทดสอบ**
ส่วนสำคัญของเกม เช่น GameState และ Core Logic ต้องมี Unit Test เพื่อทดสอบทั้ง

- กรณีที่เกมทำงานถูกต้อง (Happy Path)
- กรณีที่ข้อมูลผิดหรือเกิดข้อผิดพลาด (Unhappy Path)

**มาตรฐานโค้ด**
ก่อนนำโค้ดเข้าโปรเจกต์ ต้องตรวจสอบให้ผ่าน

- ESLint
- TypeScript Compiler (tsc --noEmit)
- Prettier

และใช้ Husky + Lint-Staged เพื่อช่วยตรวจและจัดรูปแบบโค้ดก่อน Commit

**ข้อกำหนดการใช้งาน Git และการส่งงาน**

- ห้ามแก้ไขหรือ Push โค้ดขึ้นกิ่ง main และ demo โดยตรง
- การพัฒนาฟีเจอร์ใหม่ให้แตกกิ่งตามประเภทงาน (feature/, bugfix/, refactor/)
- ส่งมอบงานผ่าน Pull Request (PR) พร้อมระบุ Description อธิบายการเปลี่ยนแปลง เหตุผล และผลการทดสอบ
- ข้อความการบันทึก (Commit Message) ต้องเป็นไปตามมาตรฐาน Conventional Commits (เช่น feat:, fix:, refactor:, test:, docs:)
- ต้องได้รับการตรวจสอบและอนุมัติจากสมาชิกในทีมอย่างน้อย 1 คนก่อนรวมกิ่ง (Merge)

## Game Rules

**กติกาการเล่น**

1. **สร้างห้องและเข้าร่วมเกม (Lobby)**
   เริ่มเกมโดยให้ผู้เล่นคนหนึ่งเป็น Host สำหรับสร้างห้องและกำหนดค่า Boot เช่น 50 ชิป
   ผู้เล่นคนอื่นสามารถใช้ Room ID เพื่อเข้ามาในห้องได้ โดยในหนึ่งห้องสามารถเล่นได้ 2–4 คน จะเริ่มเกมได้เมื่อมีผู้เล่นไม่ต่ำกว่า 2 คน เมื่อผู้เล่นเข้าครบและทุกคนพร้อม Host สามารถกด Start Game เพื่อเริ่มเกมได้

2. **จ่ายค่า Boot เข้ากองกลาง**
   เมื่อเริ่มเกม ระบบจะหักชิปจากผู้เล่นทุกคนในจำนวนเท่ากันตามค่า Boot ที่ตั้งไว้ แล้วนำไปรวมกันเป็น Pot (กองกลาง)
   เช่น ถ้า Boot = 50 ชิป และมีผู้เล่น 4 คน จะได้ Pot เริ่มต้นเป็น 200 ชิป
   ถ้าผู้เล่นคนใดมีชิปไม่พอจ่ายค่า Boot เกมจะไม่สามารถเริ่มได้

3. **แจกไพ่**
   หลังจากจ่าย Boot แล้ว ระบบจะแจกไพ่ให้ผู้เล่นแต่ละคน 3 ใบ โดยไพ่จะคว่ำอยู่
   ตอนเริ่มต้นทุกคนจะอยู่ในสถานะ Blind หมายถึงยังไม่ได้เปิดดูไพ่ของตัวเอง

4. **Blind และ Seen**
   ระหว่างเล่น ผู้เล่นสามารถเลือกได้ว่าจะเล่นแบบ Blind หรือเปิดไพ่เป็น Seen
   - **Blind** คือยังไม่ดูไพ่ของตัวเอง โดยจะเสียเงินเดิมพันน้อยกว่า
   - **Seen** คือเปิดดูไพ่ของตัวเองแล้ว แต่ต้องจ่ายเงินเดิมพันมากกว่า Blind เป็น 2 เท่า
     ผู้เล่นที่เป็น Blind สามารถเลือกเปิดดูไพ่เมื่อถึงตาของตัวเองได้ และเมื่อเปิดแล้วจะเปลี่ยนเป็น Seen ทันที

5. **การลงเดิมพัน**
   ผู้เล่นจะเล่นตามลำดับทีละคน เมื่อถึงตาของตัวเอง สามารถเลือกการกระทำได้ เช่น
   - **CALL** – ลงเงินตามจำนวนเดิมพันที่กำหนดในรอบนั้น
   - **RAISE / BET** – เพิ่มจำนวนเงินเดิมพัน ทำให้ผู้เล่นคนอื่นต้องลงเงินเพิ่มตาม
   - **SEEN** – เปิดดูไพ่ของตัวเอง และเปลี่ยนจาก Blind เป็น Seen
   - **FOLD** – หมอบและออกจากรอบนั้น เงินที่ลงไปแล้วจะไม่สามารถนำกลับคืนมาได้
     การลงเงินของผู้เล่นจะขึ้นอยู่กับสถานะของตัวเอง ถ้าเป็น Blind จะจ่าย 1 เท่า ส่วน Seen จะจ่าย 2 เท่า

6. **การขอ SHOW**
   เมื่อเหลือผู้เล่นที่ยังไม่หมอบอยู่ 2 คนสุดท้าย สามารถใช้ SHOW เพื่อเปิดไพ่และตัดสินผู้ชนะได้
   ผู้เล่นที่เป็นฝ่ายขอ SHOW ต้องจ่ายเดิมพันของรอบนั้นก่อน จากนั้นจึงเปิดไพ่เปรียบเทียบกัน

   มีข้อกำหนดเพิ่มเติมคือ
   - ผู้เล่นที่เป็น Seen ไม่สามารถขอ SHOW ใส่ผู้เล่นที่ยังเป็น Blind ได้
   - ถ้าคะแนนของไพ่ทั้งสองฝ่าย เท่ากัน คนที่เป็นฝ่ายขอ SHOW จะเป็นฝ่ายแพ้
   - ผู้ที่ขอ SHOW ต้องมีแต้มมากกว่าอีกฝ่ายจึงจะชนะ

7. **จบเกมและรับ Pot(เงินกองกลาง)**
   **เกมสามารถจบได้ 2 แบบ**
   - **แบบที่ 1 ผู้เล่นคนอื่นหมอบหมด:** ถ้าผู้เล่นทุกคนหมอบจนเหลือผู้เล่นเพียงคนเดียว ผู้เล่นคนนั้นจะชนะทันที และได้รับเงินทั้งหมดใน Pot โดยไม่ต้องเปิดไพ่
   - **แบบที่ 2 จบด้วยการ SHOW:** เมื่อมีการเปิดไพ่ ผู้เล่นที่มีแต้มสูงกว่าจะเป็นผู้ชนะและได้รับเงินทั้งหมดใน Pot

   หลังจากแจก Pot ให้ผู้ชนะแล้ว รอบนั้นถือว่าจบ และสามารถเริ่มรอบใหม่ได้

**การเรียงลำดับของไพ่**
การตัดสินผู้ชนะจะดูจากชุดไพ่ 3 ใบของผู้เล่น โดยเรียงจาก ใหญ่ที่สุด → เล็กที่สุด

1. **ตอง (Trail)**
   - ไพ่ทั้ง 3 ใบมีแต้มเหมือนกันทั้งหมด เช่น A-A-A หรือ 7-7-7
2. **เรียงสี (Pure Sequence)**
   - ไพ่ทั้ง 3 ใบมีแต้มเรียงกัน และเป็น ดอกเดียวกันทั้งหมด เช่น A-2-3 หรือ 10-J-Q
     โดย A-2-3 ถือว่าเป็นชุดที่ใหญ่ที่สุด
3. **เรียงธรรมดา (Sequence)**
   - ไพ่ทั้ง 3 ใบมีแต้มเรียงกัน แต่เป็น คนละดอกกัน เช่น 4-5-6
4. **สี (Color)**
   - ไพ่ทั้ง 3 ใบเป็น ดอกเดียวกัน แต่แต้มไม่ได้เรียงกัน เช่น A-7-10 ที่เป็นดอกเดียวกันทั้งหมด
5. **คู่ (Pair)**
   - มีไพ่ที่แต้มเหมือนกัน 2 ใบ และอีก 1 ใบเป็นแต้มอื่น เช่น K-K-5
6. **ไพ่สูง (High Card)**
   - ไพ่ไม่เข้าข่ายชุดใดเลย จึงใช้แต้มของไพ่ในการตัดสิน โดยดูจากไพ่ที่มีแต้มสูงที่สุดก่อน
     A ถือเป็นไพ่แต้มสูงสุด
     ถ้าผู้เล่นมีชุดไพ่ประเภทเดียวกัน จะต้องเปรียบเทียบแต้มของไพ่ในชุดนั้นเพื่อหาผู้ชนะ

## Architecture

สถาปัตยกรรมของระบบได้รับการออกแบบตามหลักการวิศวกรรมซอฟต์แวร์ เพื่อความเป็นระเบียบ ความง่ายต่อการบำรุงรักษา และรองรับการขยายขีดความสามารถของระบบในอนาคต:

1. **การแบ่งแยกส่วนหน้าที่ (Separation of Concerns):**
   แยกส่วนติดต่อผู้ใช้และการเรนเดอร์หน้าจอ (Presentation Layer บน Terminal) ออกจากตรรกะการประมวลผลและการตัดสินผลของเกม (Business Logic Layer บนเซิร์ฟเวอร์) โดยฝั่งเซิร์ฟเวอร์จัดหมวดหมู่โครงสร้างเป็นชั้นชัดเจน ได้แก่ กติกาหลัก (`01-Source-code/server/core/`), แบบจำลองสถานะของระบบ (`01-Source-code/server/domain/`), การควบคุมการเชื่อมต่อเครือข่าย (`01-Source-code/server/network/`) และการจัดการข้อมูล (`01-Source-code/server/infrastructure/`)

2. **การพัฒนาที่รองรับการทดสอบ (Test-Driven Development - TDD):**
   ตรรกะการประมวลผลกติกาเกมถูกแยกเป็นอิสระ ไม่ผูกติดกับ WebSocket Server หรือไลบรารีแสดงผลของเทอร์มินัล ส่งผลให้สามารถเขียนชุดทดสอบระดับหน่วย (Unit Test) ครอบคลุมทั้งกรณีการทำงานปกติ (Happy Path), กรณีเกิดข้อผิดพลาด (Unhappy Path) และกรณีขอบเขตของข้อมูล (Boundary Cases) ได้อย่างมีประสิทธิภาพ

3. **สัญญาข้อมูลร่วมระหว่างระบบ (Single Source of Truth / Shared Contracts):**
   ใช้ไดเรกทอรี `01-Source-code/shared/` เป็นศูนย์กลางในการกำหนดข้อกำหนดเชิงโครงสร้าง (TypeScript Interfaces / Types), Data Transfer Objects (DTOs) และรูปแบบข้อความเหตุการณ์ของ WebSocket (Event Payloads) เพื่อให้การแลกเปลี่ยนข้อมูลระหว่าง Client และ Server สอดคล้องกันอย่างถูกต้อง

4. **การประยุกต์ใช้กระบวนทัศน์การเขียนโปรแกรมเชิงวัตถุและเชิงฟังก์ชัน:**
   - **การเขียนโปรแกรมเชิงวัตถุ (Object-Oriented Programming - OOP):**
     นำมาใช้ในการจัดการสถานะและแบบจำลองข้อมูลใน `01-Source-code/server/domain/` โดยใช้ Class และ Interface เช่น `Player`, `Room`, `RoomManager`, `GameState` และ `GameError` เพื่อจัดการการเปลี่ยนแปลงสถานะ (State Mutation), การห่อหุ้มข้อมูลและพฤติกรรม (Encapsulation) และโครงสร้างลำดับชั้นของข้อผิดพลาด (Error Hierarchy)
   - **การเขียนโปรแกรมเชิงฟังก์ชัน (Functional Programming - FP):**
     นำมาใช้ในส่วนคำนวณและประเมินผลกติกาเกมใน `01-Source-code/server/core/gameLogic.ts` โดยเขียนในรูปแบบ **ฟังก์ชันบริสุทธิ์ (Pure Functions)** ที่ไม่มีผลข้างเคียง (Side Effects) เช่น `createDeck()`, `shuffleDeck()`, `dealCards()`, `compareHands()`, `evaluateHand()` และ `calculateSplitPot()` พร้อมทั้งใช้ **ฟังก์ชันลำดับสูง (Higher-Order Functions)** เช่น `.map()`, `.filter()`, `.some()`, `.sort()` ในการประมวลผลชุดข้อมูลไพ่
   - **การแยกส่วนตรรกะออกจากกระบวนการรับส่งข้อมูล (Decoupled Logic & I/O):**
     ฟังก์ชันคำนวณและตัดสินผลทั้งหมดปราศจากการเรียกใช้ Network Socket, File System หรือกระบวนการเรนเดอร์หน้าจอ

5. **การคงอยู่ของข้อมูล (Data Persistence):**
   - มีระบบจัดเก็บและโหลดข้อมูลเซสชันของผู้เล่น (`Session_Default`) ในรูปแบบไฟล์ JSON เพื่อสนับสนุนการเชื่อมต่อกลับเข้าสู่ห้องเดิม (Reconnection)
   - มีระบบบันทึกประวัติผลการแข่งขันเมื่อสิ้นสุดรอบลงในไฟล์ JSON บนเซิร์ฟเวอร์

## How to run

คำสั่งที่ใช้ในการตรวจสอบและเริ่มการทำงานของระบบ:

- `bunx tsc --noEmit` : ตรวจสอบความถูกต้องของประเภทข้อมูล TypeScript ทั่วทั้งโครงการโดยไม่คอมไพล์เป็นไฟล์
- `bun run lint` : ตรวจสอบรูปแบบโค้ดตามข้อกำหนดของ ESLint
- `bun run lint:fix` : ดำเนินการแก้ไขข้อผิดพลาดตามกฎ ESLint โดยอัตโนมัติในส่วนที่รองรับ
- `bunx prettier --check .` : ตรวจสอบการจัดรูปแบบไฟล์เอกสารและซอร์สโค้ดตามข้อกำหนด Prettier
- `bun run format` : จัดรูปแบบโค้ดอัตโนมัติทั่วทั้งโครงการ
- `bunx prettier --write 01-Source-code/server/core/gameLogic.ts` : จัดรูปแบบโค้ดเฉพาะไฟล์ที่ระบุ
- `bun run server` : เริ่มการทำงานของ WebSocket Server
- `bun run dev` : เริ่มการทำงานของ Client Terminal UI

```text
02-Tests/

│   │   └── gameLogic/      # ชุดทดสอบกติกาไพ่และการตัดสินผล
│   ├── domain/             # ชุดทดสอบ Domain Models และการจัดการสถานะ
│   │   ├── gameState/      # ชุดทดสอบวัฏจักรสถานะของเกม (Game Lifecycle)
│   │   │   └── fixtures/   # ชุดข้อมูลจำลองสำหรับทดสอบ GameState
│   │   └── ...
│   ├── infrastructure/     # ชุดทดสอบระบบจัดเก็บข้อมูล (Storage & Persistence)
│   ├── network/            # ชุดทดสอบการจัดการ Socket ฝั่งเซิร์ฟเวอร์
│   └── utils/              # ชุดทดสอบฟังก์ชันช่วยเหลือ
│
└── client/                 # ชุดทดสอบระบบฝั่งไคลเอนต์
    └── network/            # ชุดทดสอบการเชื่อมต่อ Socket ฝั่งไคลเอนต์
```

โครงการใช้ตัวดำเนินการทดสอบในตัวของ Bun (`bun test`) ซึ่งผ่านการทดสอบทั้งหมด 536 ชุดทดสอบ (536 passing):

- **รันชุดทดสอบทั้งหมด:** `bun test` หรือ `bun run test`
- **รันเฉพาะส่วนเซิร์ฟเวอร์:** `bun run test:server`
- **รันเฉพาะส่วนไคลเอนต์:** `bun run test:client`
- **รันเฉพาะโมเดล Player:** `bun run test:player`
- **รันเฉพาะโมเดล GameState:** `bun run test:game-state`
- **รันเฉพาะ Core GameLogic:** `bun run test:logic`
- **รันเฉพาะระบบ Schema:** `bun run test:schema`
- **รันเฉพาะระบบ Validator:** `bun run test:validator`

สามารถระบุพาธของไฟล์ทดสอบเพื่อรันเฉพาะไฟล์ได้โดยตรง เช่น:
`bun test ./02-Tests/server/domain/player/player.money.test.ts`

## Known Limitations

ข้อจำกัดทางเทคนิคและแนวทางการพัฒนาต่อยอดของระบบ:

1. **ความสมบูรณ์ของข้อมูลเซสชันในสภาวะการตัดการเชื่อมต่อเฉียบพลัน (Session Persistence Edge Case):**
   ในกรณีที่ผู้เล่นขาดการเชื่อมต่ออย่างกะทันหันก่อนที่กระบวนการตั้งค่าผู้เล่นจะเสร็จสมบูรณ์ อาจส่งผลให้ข้อมูล `PlayerName` ในไฟล์เซสชัน JSON ถูกบันทึกเป็นค่าว่าง ในการพัฒนาขั้นถัดไปควรเพิ่มกระบวนการตรวจสอบความถูกต้องของข้อมูลก่อนเขียนลงไฟล์ (Pre-write Validation)
2. **ขีดความสามารถในการรองรับการขยายตัว (Scalability):**
   สถาปัตยกรรมเซิร์ฟเวอร์ในปัจจุบันทำงานแบบ Single Instance บนหน่วยความจำเดียว (In-Memory State ร่วมกับไฟล์บันทึก JSON) เหมาะสำหรับการแข่งขันในเครือข่ายเฉพาะหรือกลุ่มย่อย (2–4 ผู้เล่นต่อห้อง) หากต้องการรองรับห้องแข่งขันจำนวนมากในระดับ Production ควรพัฒนาต่อยอดโดยใช้ระบบจัดการสถานะแบบกระจายศูนย์ (Distributed State เช่น Redis)
3. **การส่งผ่านสถานะในส่วนติดต่อผู้ใช้ (UI Component State Propagation):**
   คอมโพเนนต์บน Terminal (Ink) มีการแยกเป็นไฟล์ย่อยจำนวนมากเพื่อให้อ่านง่าย ส่งผลให้การส่งผ่าน Props ข้ามลำดับชั้นมีความซับซ้อน สามารถพัฒนาปรับปรุงได้โดยนำ State Management หรือ Context API มาใช้จัดการสถานะส่วนกลาง
