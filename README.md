# Indian Poker Online (Console Game) 🃏

## Game Overview

เกมไพ่ Indian Poker Online แบบ Multiplayer ที่เล่นผ่านหน้าจอ Console หรือ Terminal โดยไม่ใช้เว็บบราวเซอร์ ใช้วิธีการเชื่อมต่อแบบ Client-Server ผ่าน WebSocket เพื่อสื่อสารกันแบบ Real-time ทำให้สามารถรองรับผู้เล่นหลายคนพร้อมกันได้

เทคโนโลยีและโครงสร้างหลักของระบบเขียนด้วย TypeScript และรันบน Bun โดยใช้ React+Ink ในการวาดหน้าจอ Terminal ฝั่งผู้เล่น ส่วนฝั่ง Server ออกแบบให้แยกส่วนของกติกาเกม (Game Logic) ออกมาอย่างชัดเจน เพื่อให้สามารถทำ Unit Test (TDD) และตรวจสอบความถูกต้องของระบบได้อย่างแม่นยำ

## รูปแบบการเล่นในแต่ละรอบเกม

1. สร้างห้อง / เข้าห้อง
2. ทุกคนลงขัน Boot เข้าสู่ Pot
3. แจกไพ่คว่ำหน้าคนละ 3 ใบ
4. วนเทิร์นเดิมพัน โดยเลือกว่าจะเป็น Blind หรือ Seen
5. สามารถ บัฟ / ตาม / เกทับ / หมอบ
6. เมื่อเหลือผู้เล่น 2 คน สามารถ SHOW หรือหากผู้เล่นคนอื่นหมอบจนเหลือผู้เล่นคนสุดท้าย ผู้เล่นคนนั้นจะชนะ
7. ผู้ชนะรับเงินทั้งหมดใน Pot แล้วเริ่มรอบใหม่

## จุดเด่นของเกม

Blind vs Seen เป็นหัวใจหลักของเกม ความสนุกไม่ได้อยู่เพียงแค่ว่าใครได้ไพ่ดีกว่า แต่อยู่ที่การวัดใจและการตัดสินใจของผู้เล่น

- **Blind** — ผู้เล่นที่ไม่ดูไพ่ของตัวเอง จะจ่ายเงินเดิมพันถูกกว่าผู้เล่นที่ Seen โดยสามารถเกทับเพื่อกดดันผู้เล่นคนอื่นได้
- **Seen** — ผู้เล่นที่ดูไพ่ของตัวเองแล้ว แม้จะรู้หน้าไพ่ แต่ต้องรับความเสี่ยงด้วยการจ่ายเงินเดิมพันแพงกว่าผู้เล่น Blind

## อินเทอร์เฟซแบบ Terminal ยุคใหม่

ระบบใช้ React + Ink ในการสร้างหน้าจอเกมบน Terminal แทนการใช้หน้าจอ Console แบบข้อความธรรมดา โดยใช้ Component ของ React ในการวาดกระดานและปุ่มกด ทำให้หน้าจอมีความเป็นระเบียบและใช้งานง่าย

## ระบบป้องกันการโกง

ฝั่ง Client จะไม่มีทางรู้ไพ่ของคู่แข่งจนกว่าจะจบรอบและมีการเปิดไพ่จริง เนื่องจาก Server จะตัดข้อมูลไพ่ของผู้เล่นคนอื่นออกก่อนส่งข้อมูลผ่านเครือข่ายเสมอ

## ระบบรองรับการหลุดแล้วต่อใหม่

ระบบมี Session Token ที่ช่วยให้ผู้เล่นที่อินเทอร์เน็ตหลุดสามารถกลับเข้ามาเล่นต่อในตำแหน่งเดิมได้ทันที โดยไม่จำเป็นต้องเริ่มเกมใหม่

## โครงสร้างการทำงานของระบบ

ระบบแบ่งหน้าที่หลักออกเป็น 3 ส่วน

**Client**
ทำหน้าที่:

- แสดงหน้าจอเกม
- รับคำสั่งจากผู้เล่น
- ส่ง Action ไปยัง Server

**Server**
เป็นส่วนที่ควบคุมเกมทั้งหมด เช่น:

- ตรวจสอบว่า Action สามารถทำได้หรือไม่
- คำนวณการเดิมพัน
- จัดการไพ่
- ตัดสินผู้ชนะ

**Game Logic / Game State**
เก็บกติกาและสถานะของเกม เช่น:

- จำนวน Chips ของผู้เล่น
- ไพ่
- จำนวนเงินใน Pot
- ผู้เล่นที่กำลังเล่น
- ลำดับเทิร์น

## เป้าหมายของเกม

เป้าหมายหลักของผู้เล่นคือ ชนะและรับเงินทั้งหมดใน Pot
สามารถชนะได้จาก 2 วิธี:

1. ทำให้ผู้เล่นคนอื่น FOLD จนเหลือตัวเองเป็นผู้เล่นคนสุดท้าย
2. เล่นจนเหลือผู้เล่น 2 คน แล้ว SHOW เพื่อเปิดไพ่เปรียบเทียบกัน และเป็นฝ่ายที่มีไพ่ใหญ่กว่า

## Requirements

### 1. ระบบการเล่นเกม

**ระบบห้องและผู้เล่น**

- ผู้เล่นสามารถสร้างห้องและตั้งค่า Boot Amount ได้เอง
- ในหนึ่งห้องสามารถมีผู้เล่นได้ 2 – 4 คน
- ต้องมีผู้เล่นอย่างน้อย 2 คน จึงจะสามารถเริ่มเกมได้
- ถ้ามีผู้เล่นเข้ามาระหว่างที่เกมกำลังเล่นอยู่ ผู้เล่นคนนั้นจะต้องรอจนกว่ารอบปัจจุบันจะจบก่อน จึงจะสามารถเล่นได้

**ระบบไพ่และการเดิมพัน**

- ใช้ไพ่มาตรฐานทั้งหมด 52 ใบ และแจกให้ผู้เล่นคนละ 3 ใบ
- ระบบสับไพ่ต้องสามารถกำหนด Seed/RNG ได้ เพื่อให้สามารถควบคุมผลลัพธ์และใช้ในการทดสอบระบบได้
- ตอนเริ่มรอบ ผู้เล่นทุกคนจะเป็น Blind และจ่ายเดิมพันในราคาปกติ
- เมื่อผู้เล่นเลือก SEEN เพื่อเปิดดูไพ่ของตัวเอง จะเปลี่ยนเป็น Seen และต้องจ่ายเดิมพันเป็น 2 เท่าตลอดรอบนั้น
- ผู้เล่นสามารถเลือกคำสั่งต่าง ๆ ได้ เช่น CALL, BET, RAISE, FOLD, SEEN และ SHOW

**การขอ SHOW**

- สามารถขอ SHOW ได้เมื่อเหลือผู้เล่นที่ยังเล่นอยู่เพียง 2 คน
- ผู้เล่นที่เป็น Seen ไม่สามารถขอ SHOW ใส่ผู้เล่นที่ยังเป็น Blind ได้
- หากคะแนนไพ่เสมอกัน คนที่เป็นฝ่ายขอ SHOW จะถือว่าแพ้

**การเรียงลำดับไพ่**
ลำดับไพ่จากใหญ่ไปเล็กคือ
ตอง > เรียงสี > เรียงธรรมดา > สี > คู่ > ไพ่สูง
โดยมีเงื่อนไขพิเศษคือ A-2-3 ถือเป็นไพ่เรียงที่ใหญ่ที่สุด และใหญ่กว่า A-K-Q

**การแบ่งเงินใน Pot**

- ถ้าผู้เล่นคนอื่นหมอบหมด ผู้เล่นที่เหลือจะได้รับเงินใน Pot ทั้งหมด
- ถ้ามีการเปิดไพ่ ผู้เล่นที่ชนะจะได้รับเงินใน Pot
- หากมีกรณีที่ต้องแบ่งเงิน ระบบต้องรองรับการ Split Pot และจัดการเศษเงินให้ถูกต้อง

### 2. ระบบความปลอดภัยและความถูกต้อง

Server จะเป็นตัวหลักในการตัดสินทุกอย่าง เช่น

- ใครเป็นผู้ชนะ
- ผู้เล่นมีชิปเท่าไหร่
- ใครสามารถลงเดิมพันได้
- เกมอยู่ในสถานะไหน

ส่วน Client มีหน้าที่ส่งคำสั่งไปให้ Server และนำผลที่ Server ส่งกลับมาแสดงบนหน้าจอเท่านั้น

**การซ่อนไพ่**
ไพ่ของผู้เล่นต้องไม่ถูกส่งไปให้ผู้เล่นคนอื่นเห็นโดยเด็ดขาด

- ถ้ายังเป็น Blind จะยังไม่ส่งข้อมูลไพ่ให้เห็น
- ผู้เล่นจะเห็นไพ่ของตัวเองได้เมื่อเลือก SEEN
- ไพ่ของผู้เล่นทุกคนจะถูกเปิดเผยพร้อมกันเมื่อเกมจบและเข้าสู่หน้า `GAME_RESULT`

**การตรวจสอบข้อมูล**
ระบบต้องตรวจสอบข้อมูลก่อนนำไปใช้งาน เช่น

- ห้ามลงเงินติดลบ
- ห้ามใช้ตัวเลขที่มีทศนิยมถ้าระบบกำหนดให้ใช้จำนวนเต็ม
- ห้ามลงเงินเกินจำนวนที่กำหนด
- ห้ามมีไพ่ใบเดียวกันซ้ำกัน
- ถ้าเกิดข้อผิดพลาด ระบบต้องไม่ทำให้จำนวนเงินหรือสถานะเกมเสียหาย

### 3. ระบบเชื่อมต่อและการบันทึกเกม

**WebSocket**
เกมจะใช้ WebSocket สำหรับติดต่อระหว่าง Client กับ Server เพื่อให้ข้อมูลในเกมอัปเดตแบบ Real-time เช่น การลงเดิมพัน การหมอบ หรือการเปลี่ยนสถานะของผู้เล่น

**Reconnect**
เมื่อผู้เล่นเข้าห้อง ระบบจะสร้าง `reconnectToken` ให้
ถ้าอินเทอร์เน็ตหลุด ผู้เล่นสามารถใช้ Token เดิมเพื่อกลับเข้าห้องและเล่นต่อจากสถานะเดิมได้

**Save / Load**
ระบบสามารถบันทึกสถานะเกมเป็นไฟล์ JSON และสามารถโหลดกลับมาเล่นต่อได้ โดยข้อมูลสำคัญ เช่น ไพ่ ชิป และสถานะของเกมต้องไม่หาย

**ระบบแชท**
ผู้เล่นสามารถส่งข้อความพูดคุยกันภายในห้องระหว่างเล่นเกมได้

### 4. หน้าจอของเกม

ตัวเกมทำงานบน Console / Terminal โดยใช้ React 19 + Ink 7 แบ่งหน้าจอหลักออกเป็น 3 ส่วน

**LobbyScreen**
ใช้สำหรับ

- สร้างห้อง
- เข้าห้องด้วย Room ID
- ดูรายชื่อผู้เล่น
- รอผู้เล่นคนอื่นเข้าห้อง
- เริ่มเกม

**GameScreen**
เป็นหน้าหลักระหว่างเล่นเกม ใช้แสดง

- เงินใน Pot
- รายชื่อผู้เล่น
- จำนวนชิปของแต่ละคน
- สถานะ Blind / Seen
- ไพ่ของผู้เล่น
- คำสั่งที่สามารถเลือกได้ เช่น CALL, BET, RAISE, FOLD, SEEN และ SHOW

**ResultScreen**
แสดงผลหลังจบเกม เช่น

- ใครเป็นผู้ชนะ
- ผู้ชนะได้รับชิปเท่าไหร่
- ไพ่ของผู้เล่นแต่ละคน
- ผลการเปิดไพ่
- สรุปผลของรอบนั้น

### 5. มาตรฐานในการพัฒนา

**การทดสอบ**
ส่วนสำคัญของเกม เช่น GameState และ Core Logic ต้องมี Unit Test เพื่อทดสอบทั้ง

- กรณีที่เกมทำงานถูกต้อง (Happy Path)
- กรณีที่ข้อมูลผิดหรือเกิดข้อผิดพลาด (Unhappy Path)

**มาตรฐานโค้ด**
ก่อนนำโค้ดเข้าโปรเจกต์ ต้องตรวจสอบให้ผ่าน

- ESLint
- TypeScript Compiler (tsc --noEmit)
- Prettier

และใช้ Husky + Lint-Staged เพื่อช่วยตรวจและจัดรูปแบบโค้ดก่อน Commit

**การใช้ Git**
ไม่ควรแก้ไข main และ demo โดยตรง
เวลาจะพัฒนาฟีเจอร์ใหม่ ให้สร้าง Branch แยกออกมาก่อน จากนั้นเปิด Pull Request เพื่อให้ทีมตรวจสอบ และต้องมีสมาชิกอย่างน้อย 1 คนอนุมัติก่อนจึงจะ Merge ได้

## Game Rules

**กติกาการเล่น**

1. **สร้างห้องและเข้าร่วมเกม (Lobby)**
   เริ่มเกมโดยให้ผู้เล่นคนหนึ่งเป็น Host สำหรับสร้างห้องและกำหนดค่า Boot เช่น 50 ชิป
   ผู้เล่นคนอื่นสามารถใช้ Room ID เพื่อเข้ามาในห้องได้ โดยในหนึ่งห้องสามารถเล่นได้ 2–4 คน จะเริ่มเกมได้เมื่อมีผู้เล่นไม่ต่ำกว่า 2 คน เมื่อผู้เล่นเข้าครบและทุกคนพร้อม Host สามารถกด Start Game เพื่อเริ่มเกมได้

2. **จ่ายค่า Boot เข้ากองกลาง**
   เมื่อเริ่มเกม ระบบจะหักชิปจากผู้เล่นทุกคนในจำนวนเท่ากันตามค่า Boot ที่ตั้งไว้ แล้วนำไปรวมกันเป็น Pot (กองกลาง)
   เช่น ถ้า Boot = 50 ชิป และมีผู้เล่น 4 คน จะได้ Pot เริ่มต้นเป็น 200 ชิป
   ถ้าผู้เล่นคนใดมีชิปไม่พอจ่ายค่า Boot เกมจะไม่สามารถเริ่มได้

3. **แจกไพ่**
   หลังจากจ่าย Boot แล้ว ระบบจะแจกไพ่ให้ผู้เล่นแต่ละคน 3 ใบ โดยไพ่จะคว่ำอยู่
   ตอนเริ่มต้นทุกคนจะอยู่ในสถานะ Blind หมายถึงยังไม่ได้เปิดดูไพ่ของตัวเอง

4. **Blind และ Seen**
   ระหว่างเล่น ผู้เล่นสามารถเลือกได้ว่าจะเล่นแบบ Blind หรือเปิดไพ่เป็น Seen
   - **Blind** คือยังไม่ดูไพ่ของตัวเอง โดยจะเสียเงินเดิมพันน้อยกว่า
   - **Seen** คือเปิดดูไพ่ของตัวเองแล้ว แต่ต้องจ่ายเงินเดิมพันมากกว่า Blind เป็น 2 เท่า
     ผู้เล่นที่เป็น Blind สามารถเลือกเปิดดูไพ่เมื่อถึงตาของตัวเองได้ และเมื่อเปิดแล้วจะเปลี่ยนเป็น Seen ทันที

5. **การลงเดิมพัน**
   ผู้เล่นจะเล่นตามลำดับทีละคน เมื่อถึงตาของตัวเอง สามารถเลือกการกระทำได้ เช่น
   - **CALL** – ลงเงินตามจำนวนเดิมพันที่กำหนดในรอบนั้น
   - **RAISE / BET** – เพิ่มจำนวนเงินเดิมพัน ทำให้ผู้เล่นคนอื่นต้องลงเงินเพิ่มตาม
   - **SEEN** – เปิดดูไพ่ของตัวเอง และเปลี่ยนจาก Blind เป็น Seen
   - **FOLD** – หมอบและออกจากรอบนั้น เงินที่ลงไปแล้วจะไม่สามารถนำกลับคืนมาได้
     การลงเงินของผู้เล่นจะขึ้นอยู่กับสถานะของตัวเอง ถ้าเป็น Blind จะจ่าย 1 เท่า ส่วน Seen จะจ่าย 2 เท่า

6. **การขอ SHOW**
   เมื่อเหลือผู้เล่นที่ยังไม่หมอบอยู่ 2 คนสุดท้าย สามารถใช้ SHOW เพื่อเปิดไพ่และตัดสินผู้ชนะได้
   ผู้เล่นที่เป็นฝ่ายขอ SHOW ต้องจ่ายเดิมพันของรอบนั้นก่อน จากนั้นจึงเปิดไพ่เปรียบเทียบกัน

   มีข้อกำหนดเพิ่มเติมคือ
   - ผู้เล่นที่เป็น Seen ไม่สามารถขอ SHOW ใส่ผู้เล่นที่ยังเป็น Blind ได้
   - ถ้าคะแนนของไพ่ทั้งสองฝ่าย เท่ากัน คนที่เป็นฝ่ายขอ SHOW จะเป็นฝ่ายแพ้
   - ผู้ที่ขอ SHOW ต้องมีแต้มมากกว่าอีกฝ่ายจึงจะชนะ

7. **จบเกมและรับ Pot(เงินกองกลาง)**
   **เกมสามารถจบได้ 2 แบบ**
   - **แบบที่ 1 ผู้เล่นคนอื่นหมอบหมด:** ถ้าผู้เล่นทุกคนหมอบจนเหลือผู้เล่นเพียงคนเดียว ผู้เล่นคนนั้นจะชนะทันที และได้รับเงินทั้งหมดใน Pot โดยไม่ต้องเปิดไพ่
   - **แบบที่ 2 จบด้วยการ SHOW:** เมื่อมีการเปิดไพ่ ผู้เล่นที่มีแต้มสูงกว่าจะเป็นผู้ชนะและได้รับเงินทั้งหมดใน Pot

   หลังจากแจก Pot ให้ผู้ชนะแล้ว รอบนั้นถือว่าจบ และสามารถเริ่มรอบใหม่ได้

**การเรียงลำดับของไพ่**
การตัดสินผู้ชนะจะดูจากชุดไพ่ 3 ใบของผู้เล่น โดยเรียงจาก ใหญ่ที่สุด → เล็กที่สุด

1. **ตอง (Trail)**
   - ไพ่ทั้ง 3 ใบมีแต้มเหมือนกันทั้งหมด เช่น A-A-A หรือ 7-7-7
2. **เรียงสี (Pure Sequence)**
   - ไพ่ทั้ง 3 ใบมีแต้มเรียงกัน และเป็น ดอกเดียวกันทั้งหมด เช่น A-2-3 หรือ 10-J-Q
     โดย A-2-3 ถือว่าเป็นชุดที่ใหญ่ที่สุด
3. **เรียงธรรมดา (Sequence)**
   - ไพ่ทั้ง 3 ใบมีแต้มเรียงกัน แต่เป็น คนละดอกกัน เช่น 4-5-6
4. **สี (Color)**
   - ไพ่ทั้ง 3 ใบเป็น ดอกเดียวกัน แต่แต้มไม่ได้เรียงกัน เช่น A-7-10 ที่เป็นดอกเดียวกันทั้งหมด
5. **คู่ (Pair)**
   - มีไพ่ที่แต้มเหมือนกัน 2 ใบ และอีก 1 ใบเป็นแต้มอื่น เช่น K-K-5
6. **ไพ่สูง (High Card)**
   - ไพ่ไม่เข้าข่ายชุดใดเลย จึงใช้แต้มของไพ่ในการตัดสิน โดยดูจากไพ่ที่มีแต้มสูงที่สุดก่อน
     A ถือเป็นไพ่แต้มสูงสุด
     ถ้าผู้เล่นมีชุดไพ่ประเภทเดียวกัน จะต้องเปรียบเทียบแต้มของไพ่ในชุดนั้นเพื่อหาผู้ชนะ

## Architecture

วางโครงสร้าง วางระเบียบ และกำหนดทิศทาง ในการพัฒนา เพื่อให้โค้ดมีความเป็นระเบียบ ทำงานร่วมกันในทีมได้ง่าย และขยายระบบต่อได้ในอนาคต

1. **การแยกส่วน:** คือ แยกฝั่งหน้าจอแสดงผลออกจากระบบประมวลผลเกม อย่างชัดเจน ช่วยให้ปรับแต่งหรือรื้อทำ UI ใหม่ได้เรื่อย ๆ โดยไม่กระทบกับกติกาเดิมของเกม Layering Inside Server ออกแบบโครงสร้างภายในเซิร์ฟเวอร์แยกเป็นชั้นชัดเจน แบ่งโค้ดส่วนกติกาหลัก (Core), สถานะของเกม (Domain), ระบบรับส่งข้อมูล (Network) และการจัดการฐานข้อมูล (Infrastructure) ออกจากกัน

2. **สนับสนุนการพัฒนาแบบ TDD:** ช่วยให้เขียน Unit Test ง่ายขึ้น พอเราออกแบบสถาปัตยกรรมให้โค้ดส่วนกติกาเกม (`src/server/core/`) แยกเป็นอิสระจากส่วนอื่น (ไม่ต้องไปผูกกับ WebSocket หรือหน้าจอ UI) มันเลยทำให้เราเขียน Unit Test ได้สะดวก เราสามารถโยนเคสแปลกๆ หรือ Test Case ยากๆ เข้าไปเช็กความถูกต้องของ Logic เกมได้ทันที ทั้งเร็ว ทั้งแม่นยำ โดยไม่ต้องคอยเปิดหน้าจอเล่นเอง

3. **กำหนดมาตรฐานการสื่อสาร:** มี Single Source of Truth สำหรับโครงสร้างข้อมูล เราใช้ `src/shared/` เป็นตัวกลางกำหนดพวก Data Types และ Format ของข้อความ WebSocket พอมันใช้โครงสร้างเดียวกันทั้ง Client และ Server เวลาพัฒนาก็จะคุยกันรู้เรื่อง ข้อมูลที่รับส่งกันก็ถูกต้องแม่นยำ ไม่ต้องมานั่งเดาหรือเจอบั๊กแปลกๆ ที่เกิดจากประเภทข้อมูลไม่ตรง

4. **ให้ระบบขยายต่อและดูแลรักษาง่าย (Maintainability & Scalability):** เมื่อโปรเจกต์มีผู้พัฒนาร่วมกันหลายคน การมี Architecture ที่ชัดเจนจะทำให้ เพิ่มฟีเจอร์ใหม่ได้ง่ายโดยไม่กระทบโค้ดเดิม ค้นหาและแก้ไขบั๊ก (Bug) ได้ตรงจุด สมาชิกใหม่ในทีมเข้าใจโครงสร้างและเริ่มเขียนโค้ดต่อได้เร็ว

## How to run

- `bunx tsc --noEmit` : ตรวจสอบข้อผิดพลาดของ TypeScript โดยไม่ Compile ไฟล์
- `bun run lint` : ตรวจสอบข้อผิดพลาดตามกฎ ESLint
- `bun run lint:fix` : สั่งแก้ปัญหา ESLint อัตโนมัติในส่วนที่แก้ไขได้
- `bunx prettier --check .` : ตรวจสอบ Format โค้ดทั้งโปรเจกต์จะไม่มีการแก้ไฟล์ คือให้มันไปตรวจว่า การเว้นวรรค การเคาะบรรทัด มันจะไปตรวจให้ว่ามีตรงไหนที่ทำไม่ดี หรือไม่ได้เคาะบรรทัด ถ้ามีมันก็จะแจ้งแต่ไม่ได้แก้ให้
- `bun run format` : จัด Format โค้ดใหม่ทั้งโปรเจกต์ (มีการเขียนทับไฟล์) จะจัดบรรทัดให้ทุกไฟล์ในโปรเจกต์ ละก็เขียนทับลงไปจากของเดิม โค้ดจะเหมือนเดิม ไม่มีการแก้ Logic อะไร แค่จัด format ให้
- `bunx prettier --write src/server/core/gameLogic.ts` : จัด Format เฉพาะไฟล์ที่ระบุ (ตัวอย่างในคำสั่งคือให้จัดโค้ดให้สวย เฉพาะ gameLogic)
- `bun run dev` : รันเกม
- `bun run server` : รันเซิฟเวอร์

## How to Test

**Test Directory Structure**  
โครงสร้างของโฟลเดอร์ Test จัดกลุ่มให้ตรงกับโครงสร้างของซอร์สโค้ด เพื่อให้อ่านง่ายและรู้ขอบเขตของแต่ละไฟล์ได้อย่างชัดเจน แยกตามฝั่ง Server และ Client ดังนี้

```text
Test/
├── server/                 # การทดสอบส่วน Backend ทั้งหมด
│   ├── core/               # ระบบ Core Logic และ Schema กลาง
│   │   └── gameLogic/      # กติกาเกม โป๊กเกอร์
│   ├── domain/             # การทดสอบ Model และ Business Logic หลัก
│   │   ├── gameState/      # State ของเกม ไหลตั้งแต่เกิดจนจบ
│   │   │   └── fixtures/   # ตัวสร้างข้อมูล Mock เฉพาะของ GameState
│   │   └── ...
│   ├── infrastructure/     # ระบบที่ต่อกับภายนอก เช่น Database, Storage
│   ├── network/            # การจัดการ Socket ฝั่ง Server
│   └── utils/              # Helper ฟังก์ชันต่างๆ
│
└── client/                 # การทดสอบฝั่ง Frontend / Client
    └── network/            # การเชื่อมต่อ Socket ฝั่ง Client
```

โปรเจกต์นี้ใช้ `bun test` เป็นตัวรันหลัก สามารถรันแยกกลุ่มได้ด้วยคำสั่งใน `package.json` ดังนี้

- **รันทั้งหมด:** `bun run test` หรือ `bun test`
- **ฝั่ง Server ทั้งหมด:** `bun run test:server`
- **ฝั่ง Client ทั้งหมด:** `bun run test:client`
- **Player:** `bun run test:player`
- **GameState:** `bun run test:game-state`
- **GameLogic:** `bun run test:logic`
- **Schema:** `bun run test:schema`
- **Validator:** `bun run test:validator`

ถ้าต้องการเจาะจงไฟล์ สามารถรันผ่าน path ได้โดยตรง เช่น
`bun test ./Test/server/domain/player/player.money.test.ts`

## Known Limitations

บอกจุดอ่อนหรือข้อจำกัดในปัจจุบัน เพื่อบริหารความคาดหวังและป้องกันปัญหาในการใช้งาน

1. **ระบุสิ่งที่ระบบยังทำไม่ได้** ก็คือแจ้งระบบที่ยังมีข้อจำกัดบางอย่างที่ยังไม่รองรับ เช่น รองรับผู้เล่นสูงสุดได้กี่คน หรือยังไม่รองรับการเชื่อมต่อใหม่หลังเน็ตหลุด
2. **ช่วยสกรีนบั๊กซ้ำและกัน QA แจ้งเปิดตั๋วซ้ำซ้อน** การลิสต์ข้อจำกัดพวกนี้ไว้ ก็เพื่อช่วยป้องกันไม่ให้พวกเราหรือทีม QA เสียเวลาเปิด Report ปัญหาที่ทีม Dev รู้อยู่แล้วว่าเป็นข้อจำกัดของเวอร์ชันปัจจุบัน จะได้เอาเวลาไปโฟกัสกับบั๊กจริง ๆ ที่หลุดมาแทน
3. **ใช้เป็น Roadmap ในการพัฒนาต่อ** เป็นรายการสิ่งที่ต้องกลับมาปรับปรุง แก้ไข หรือเพิ่มประสิทธิภาพ (Optimization) ในเฟสถัดไปของโปรเจกต์
